The threat model

An agent takes instructions from text and holds tools that act on the world. The gap between those two facts is the whole of agent security.

Two sources of unintended action:

Prompt injection. Instructions embedded in content the agent processes — a web page, a PDF, a ticket, a code comment, a filename, a memory file it wrote last week. The model cannot reliably distinguish "content to reason about" from "instructions to follow", because at the level it operates, both are text.

Model error. No adversary needed. The agent misreads a situation and takes a destructive action with complete sincerity.

Models are trained to resist injection and they are meaningfully good at it. That is a mitigation, not a control. "Usually resists" is an unacceptable property for the only thing standing between a web page and your production database — so defence in depth stands, and every layer must hold on its own.

The lethal trifecta

The single most useful security concept in this course. Three capabilities:

  1. Access to private data — files, databases, internal APIs, secrets in the environment.
  2. Exposure to untrusted content — web pages, email, tickets, documents, its own memory.
  3. Ability to communicate externally — send email, arbitrary HTTP, git push, write to any system an observer can read.

Any two are manageable. All three is an exfiltration primitive: an attacker who can place text anywhere the agent will read it can instruct it to gather your private data and send it out. No prompt fixes this, because the prompt is not the boundary.

Audit for this reflexively — on every design, and again every time someone adds a tool, connects an MCP server, or enables memory. The third leg almost never arrives in a design review. It arrives in a pull request that adds "just a webhook".

The cheapest leg to break is usually egress: allow-list destinations through a proxy. The next is untrusted content: summarise retrieved material rather than injecting it raw. The hardest is private data, because it is usually the reason the agent exists — which is what the credential proxy below is for.

Permissions are a gate, not a sandbox

Restated from M5 because this is where it costs you.

A permission rule matching bash(curl *) is doing string analysis on adversarial input. The same action can be /usr/bin/curl, $(which curl), c""url, a variable, a base64 blob piped to sh, or four lines of Python opening a socket. Every deny-list asserts you enumerated the spellings of an action. You did not.

Permissions are still worth having — they catch model error, which is most of what actually happens, and they give the user a decision point. But they stop an adversary only by luck. For that you need a boundary the process cannot argue with.

The row that misleads people is containers. A container isolates namespaces, and an unhardened one shares the kernel, often runs as root, keeps all capabilities, and has full network access. It is a packaging boundary that people mistake for a security boundary.

A container config, line by line

Every line is load-bearing. read_only plus a capped tmpfs means a compromised agent cannot persist anything. cap_drop: ALL removes the capabilities that make most escapes possible. network_mode: none means the only way out is the proxy you control — which is what makes egress control real rather than advisory. And the empty environment is the one people cannot believe: your agent does not need credentials, as the next section explains.

The credential proxy

The pattern that makes the "private data" leg tractable.

The agent never holds a secret. It makes an unauthenticated request to a local proxy; the proxy attaches credentials and forwards; the response comes back. The agent can use the API and cannot read the key.

What this buys, beyond the obvious:

  • A prompt injection that exfiltrates the environment gets nothing.
  • The allow-list is method and route, so read access does not imply write access.
  • The audit log exists by construction — it is on the only path out.
  • Rotation happens in one place, with no agent redeploy.
  • Rate limiting and quota live here too, for free.

Egress control, and its limits

With network_mode: none, all traffic goes through your proxy, and the proxy allow-lists destinations. That is genuinely strong.

Now the honest part, because a control you have overestimated is worse than one you know the limits of. Without TLS interception, you are allow-listing hostnames, not content. Consequences:

  • Domain fronting. A permitted hostname can front for a different backend.
  • Data in permitted channels. If github.com is allow-listed, data can leave inside a commit, a gist or an issue body. The destination is fine; the payload is not.
  • DNS and timing channels. Low bandwidth, entirely sufficient for an API key.

For strong guarantees you need a TLS-terminating proxy that inspects payloads — with the operational and privacy consequences that carries. Most teams accept hostname allow-listing and write the residual risk down. Writing it down is the part that matters, because an unstated assumption becomes a false claim in the next security review.

Content boundaries

Two habits that cost almost nothing and remove a large fraction of injection risk.

Summarise rather than inject. Do not paste a fetched page into context verbatim. Run it through a summarisation step first. Instructions rarely survive paraphrase — it is a weak filter, but it is free and it composes with everything else.

Mark provenance explicitly. Wrap untrusted content so its boundaries are unambiguous, and say so:

This is a mitigation, not a control. It measurably helps and it will not save you alone. Treat every tool result as untrusted — including results from your own systems, which may contain user-supplied text that arrived long before your agent did.

The read-only mount that leaked the AWS keys

A team mounted the repository read-only, reasoning that a read-only agent cannot do damage. The agent had web fetch for documentation lookups and could open pull requests.

An injection arrived in a dependency's README. It instructed the agent to read ~/.aws/credentials — outside the repo mount, but inside the container's filesystem, because only the repo was restricted — and include it in a branch it pushed.

Read-only stopped the agent modifying the repository. It stopped nothing else. The whole trifecta was present: private data (the credential file was reachable), untrusted content (the README), egress (git push). Read-only is not the same as safe, and "the agent can't write" answers a question nobody was asking.
