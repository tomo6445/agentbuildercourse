The whole problem in one sentence

An agent takes instructions from text, and holds tools that act on the world.

The idea in one line

Every document your agent reads is untrusted input to a system that holds tools.

Remember from F1: to the model, everything is text. Your instructions are text. The user's question is text. And the web page it just fetched is text.

The model has no reliable way to tell "content I should think about" from "instructions I should follow", because at the level it works, they are the same kind of thing.

Prompt injection

Instructions hidden inside content your agent reads, intended to make it do something you did not ask for.

The content can be a web page, a PDF, an email, a support ticket, a code comment, a filename — or a memory file it wrote itself last week (M7).

Models are trained to resist this and are meaningfully good at it. That is a mitigation, not protection. "Usually resists" is not an acceptable property for the only thing standing between a web page and your production database.

The three-part combination

This is the most useful idea in the module. Three capabilities:

  1. Access to private data — files, databases, internal systems, secrets in the environment.
  2. Exposure to untrusted content — web pages, email, tickets, documents, its own memory.
  3. A way to send things out — email, arbitrary web requests, pushing to a code repository.

Any two are manageable. All three is a way to steal your data.

Because with all three, anyone who can get text in front of your agent can instruct it to gather private information and send it somewhere. No hacking required. They write a sentence on a page your agent will read.

This instrument needs JavaScript. The lesson reads fine without it.

Check for this by reflex — on every design, and again every time somebody adds a tool, connects a server, or turns on memory. The third capability almost never arrives in a design review. It arrives in a change that adds "just a webhook".

Breaking one is the fix. Which one is easiest depends:

  • Sending things out is usually cheapest — allow only specific destinations, through something you control.
  • Untrusted content is next — summarise what you fetch rather than passing it through whole.
  • Private data is hardest, because it is usually why the agent exists. The credential proxy below is how you deal with it.

Rules are not walls

M5 said this; here is where it costs you.

A rule blocking commands containing curl is matching text that an attacker may be choosing. The same action can be written /usr/bin/curl, $(which curl), a shell variable, an encoded blob piped into a shell, or four lines of Python opening a network connection.

Every block-list is a claim that you thought of all the spellings. You did not.

Rules are still worth having — they catch mistakes, which is most of what actually happens, and they give a person somewhere to intervene. They stop someone trying only by luck.

For that you need a boundary the program cannot argue with.

Isolation

Sandbox

A restricted environment a program runs inside, which limits what it can reach — which files, which network, how much memory.

The point is that the restriction is enforced from outside the program. Nothing the program does, and nothing anyone persuades it to do, can lift it.

The row that misleads people is containers. A container separates names — it looks like its own machine. By default it often shares the host's core operating system, runs as the top-level user, keeps all its privileges and has full network access. It is a packaging boundary that people mistake for a security one.

A hardened configuration, line by line

Every line does work. read_only plus a small temporary space means a compromised agent cannot leave anything behind. Dropping privileges removes what most escapes rely on. network_mode: none means the only way out is something you control — which is what makes the next section real rather than advisory.

And the empty environment is the one people cannot believe.

The agent never holds a secret

The pattern that makes the "private data" leg manageable.

The agent makes unauthenticated requests to a small service you run. That service adds the credentials and forwards them. The agent can use the API and cannot read the key.

What this buys, beyond the obvious:

  • An injection that dumps the environment finds nothing.
  • The list is method and route, so being able to read does not imply being able to write.
  • The audit log exists automatically, because this is the only path out.
  • Rotating a credential happens in one place, with no agent redeployment.

Controlling what leaves, honestly

With no network in the sandbox, everything goes through your service, which permits only certain destinations. That is genuinely strong.

Now the honest part, because a control you have overestimated is worse than one whose limits you know.

You are allowing destinations, not contents

Unless you are inspecting the traffic itself, you are permitting where things go, not what goes there.

  • A permitted destination can be misused. If github.com is allowed, data can leave inside a commit, a snippet or an issue.
  • A permitted name can front something else.
  • Even DNS lookups can carry data out, slowly — and slowly is plenty for an API key.

Inspecting contents means terminating encrypted connections, with real operational and privacy consequences. Most teams allow destinations and write the remaining risk down.

Writing it down is the part that matters. An unstated assumption becomes a false claim in the next security review.

The read-only folder that leaked the keys

A team mounted the code repository read-only, reasoning that an agent that cannot write cannot do damage. It also had web fetching for documentation, and could open pull requests.

An injection arrived in a dependency's README. It told the agent to read ~/.aws/credentials — outside the repository, but inside the container's filesystem, because only the repository was restricted — and include it in a branch it pushed.

Read-only stopped the agent modifying the repository. It stopped nothing else. All three capabilities were present: private data (the credentials file was reachable), untrusted content (the README), a way out (pushing).

Read-only is not the same as safe. "The agent can't write" answers a question nobody was asking.

Building a threat model, in four questions

A threat model is a written answer to four questions. It does not need to be long; it needs to exist.

What is worth taking? Customer data, credentials, the ability to spend money, the ability to change production.

Who can put text in front of it? Every source it reads. Be exhaustive — web pages, tickets, emails, file contents, filenames, code comments, its own memory.

What can it reach? Every tool, every connected server, every file path, every network destination.

What actually stops each path? For each combination of the above, name the control — and be honest when the answer is "nothing, we accept this".

That last honesty is what makes it useful. A threat model claiming complete coverage is a document nobody trusts after the first incident.

What you now know

  • Everything is text to the model, so content and instructions are indistinguishable to it.
  • Private data + untrusted content + a way out = a way to steal your data. Check by reflex.
  • Rules catch mistakes; they do not stop attackers. Real boundaries are outside the program.
  • A default container is not a sandbox. Configuration is what makes it one.
  • A credential proxy means the agent never holds a secret.
  • You control destinations, not contents. Write down what that leaves open.
