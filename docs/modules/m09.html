The real benefit is not specialisation

The usual pitch for multi-agent systems is specialisation: a research agent, a writing agent, a critic. That framing is mostly wrong, because a single model with a good prompt can play all three roles competently.

The actual benefit is context isolation. Each sub-agent gets its own window. A worker can read twenty documents, burn 80,000 tokens exploring, and return a two-paragraph finding. The orchestrator's context grows by two paragraphs.

That is the trick. Not "the researcher is better at researching" but "the researcher's mess stays in the researcher's window."

The idea in one line

Multi-agent systems can burn many times the tokens of a single chat. The task has to be worth it.

When it works

On wide search tasks — where the work is finding and reading many sources in parallel — token budget explains most of the performance variance between systems. If the task's difficulty is proportional to how much material must be examined, then more parallel context is directly more capability.

Under those conditions, an orchestrator running a strong lead model with a pool of cheaper workers has been measured substantially ahead of a strong single agent on research benchmarks. The mechanism is unglamorous: the multi-agent system simply read more, and the lead saw only the conclusions.

The conditions that make it work, all of which must hold:

  • The task parallelises. Independent sub-questions, not a chain where step 2 needs step 1.
  • The work is read-heavy. Gathering and filtering, not a long sequence of mutations.
  • The task is valuable enough to absorb the token multiple.

When it fails

Duplicated work. Two workers given overlapping briefs run nearly the same searches and return nearly the same findings. You paid twice for one result. This is the most common failure and it is a prompt problem, not a code problem.

Contradictory findings. Worker A says the figure is 2.1B, worker B says 2.15B. Now the orchestrator must adjudicate — and its most common instinct is to average them or pick the better-written one, both of which are wrong.

Coordination overhead. Delegating, waiting, synthesising all cost turns and tokens. Below a certain task size, the overhead exceeds the benefit and one agent doing it directly is faster and better.

Synchronous bottlenecks. An orchestrator that waits for all workers runs at the speed of the slowest, and one hung worker stalls everything.

Cost. The multiple is real. Budget for it before building, not after the first invoice.

The orchestrator-worker shape

Two details in that sketch carry most of the weight. Worker failures return a marker rather than raising, so one dead worker degrades the answer instead of killing the run. And worker count is computed from the task, not fixed — which is the next section.

Delegation prompts are the hard part

This is where multi-agent systems are actually built or lost. A vague brief produces overlapping, unciteable, unusable findings, and no amount of orchestrator cleverness recovers from it.

A worker brief needs five things:

Scope with explicit negative space. "Revenue only, others are covering margins" is what prevents duplication. Without it, every worker helpfully investigates the interesting adjacent thing.

Tool restrictions per worker. Read-only workers should be read-only in configuration, not by request. This is also a security control (M11): a worker exposed to untrusted web content should not be holding write tools.

Effort scaling, stated. Without a stated expectation, workers run until they feel finished — and "finished" for a language model on an open-ended search is a long way out. Say roughly how much work this is worth.

A structured output contract. The orchestrator must merge findings. Prose does not merge.

Confidence and caveats as required fields. They give the lead something to adjudicate with when findings conflict, instead of guessing.

Synthesis is the lead's hardest job

Everything so far was preparation for this. The lead now holds N findings and must produce one answer.

Conflict resolution needs a rule, stated in advance. Prefer primary sources over secondary. Prefer recent over old for facts that change. Prefer the higher-confidence finding when sources are equally good. When a conflict cannot be resolved, surface it — "sources disagree: the 10-K says 2.1B, the press release says 2.15B" is a far better answer than a confident average.

Citations must survive. The lead is rewriting text, and rewriting is exactly when attributions get dropped. Require the synthesis to carry source references through to the final output; assert it in the eval suite.

And the failure to design against explicitly: three workers return confidently wrong findings and the lead synthesises them into a fluent, well-structured, entirely false answer. The multi-agent structure amplified the error, because agreement between workers reads as corroboration. Defences: require sources for every claim, have the lead check whether workers actually used independent sources, and treat unanimous confidence on a hard question as suspicious rather than reassuring.

The decision rule

Before you build one, three things must be true:

  1. Parallelisable — genuine independent subtasks.
  2. Read-heavy — gathering and filtering, not a mutation sequence.
  3. Worth the multiple — the value per task can absorb several times the single-agent cost.

If all three hold, build it. If not, a single agent with good context management (M3) will be cheaper, faster and easier to debug.

Two subagents, same search, twice the bill

Two workers, briefs "research the competitive landscape" and "analyse market positioning". A human reads those as different questions. The workers ran seventeen searches between them, thirteen of them identical, and returned findings that overlapped by roughly 80%.

The fix was not in code. It was a scope line in each brief naming what the other worker was covering, and a shared "already searched" list passed to each. Duplicate searches dropped to two, at no cost in quality. The lesson generalises: nearly every multi-agent efficiency bug is a delegation prompt bug, and the reflex to fix it with orchestration code is a reflex to fix it in the wrong place.
