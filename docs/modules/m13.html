The question is not "can it"

By this point in the course you can build an agent that does the task. The remaining questions are harder and they are product questions:

When should it ask? And when it asks, how does a human know whether to say yes?

The idea in one line

The hard question isn't “can the agent do it” but “when should it ask, and how does a human know whether to say yes.”

The autonomy ladder

Six rungs, from least to most autonomous:

  1. Suggest — the agent proposes, a human performs the action.
  2. Approve each — the agent proposes each action and waits.
  3. Approve risky — routine actions proceed; a defined risky class waits.
  4. Act and notify — the agent acts, the human is told afterwards.
  5. Act with undo — the agent acts, the human can reverse it.
  6. Autonomous — the agent acts; no notification, no undo.

The mistake everyone makes first is choosing a rung for the agent. It is chosen per action class, and a single agent will span four rungs at once.

The same coding agent should read files autonomously (rung 6 — approving reads is how you train people to click yes without looking), commit to a feature branch with undo (rung 5 — git makes undo cheap and real), and wait for approval before force-pushing to main (rung 2). Rating "this agent" as "semi-autonomous" is a category error that produces both over-gating and under-gating simultaneously.

Two properties place an action on the ladder: reversibility and blast radius. Cheaply reversible and self-contained goes high. Irreversible or wide goes low.

What a human needs to decide

Here is a real approval prompt, and it is a rubber-stamp generator:

A person shown that a hundred times a day learns exactly one behaviour, and it is not careful review.

Four fields make a decision possible:

The action, concretely. Not "bash" — rm -rf ./build/cache in /srv/app, affecting 340 files.

The reason. What the agent believes this accomplishes. "Clearing the stale build cache so the next compile picks up the dependency change."

The blast radius. What changes, for whom, and whether it is reversible. "Deletes generated files only; no source. Regenerated by the next build."

The alternative. What happens if you decline. "I'll skip the clean and try an incremental build, which may reproduce the error."

That fourth field is the one that is almost always missing, and it is the one that makes approval a choice rather than a gate. Without it the human has no way to weigh anything — they can only guess at the cost of saying no.

Approval fatigue is a security failure mode

State it plainly, because it is usually treated as a UX annoyance: a human who approves forty prompts a day is not reviewing anything. You have built a security control whose reliability degrades with usage, and you have done it in a way that looks responsible on an architecture diagram.

The countermeasures:

Risk tiering. Only genuinely risky actions interrupt. If everything asks, nothing is reviewed.

Batching. "The agent will modify these 12 files: [list]. Approve all?" One considered decision beats twelve reflexes.

Learned allow-lists. "You have approved npm test 23 times. Always allow?" — the honest response to a pattern the human has already established.

Scoped approvals. "Approve cache operations for this session" bounds the grant in time and kind rather than forever and everywhere.

Measure it. Track approvals per user per day, and time-to-decision. When median decision time drops below about two seconds, your control has become a formality and you should know that.

Steering and interruption

Watching an agent go the wrong way with no way to intervene except killing it is a terrible experience, and it wastes everything done so far.

Interrupt should pause cleanly at the next turn boundary, preserving state.

Steer should let a human inject a correction that the agent incorporates and continues from — "no, use the staging database" — without discarding twelve turns of context.

Rewind should let a human return to turn 8 and take a different path, which is session forking (M5) with a user interface on it.

Design steering as an operator channel rather than an ordinary user message. On supporting models, appending a {"role": "system"} message mid-conversation is exactly this: it carries operator authority, is not confusable with the untrusted user turn, and preserves the cached prefix.

Streaming UX for unknown step counts

Agents violate the two progress-bar assumptions: they do not know how many steps remain, and the steps are not equal.

What actually works:

Show the work, not a percentage. A live feed of what the agent is doing — "searching the ledger export", "reading contract.pdf (page 4 of 12)" — is more informative and more honest than a fabricated bar.

Make tool calls visible. Users trust an agent whose actions they can see, and they catch mistakes earlier. This is legibility doing security work.

Stream the reasoning where it helps. Summarised thinking makes long pauses legible. Note that on current models thinking display defaults to omitted, so a streaming UI shows a long silence unless you explicitly ask for the summary.

Be honest about the unknown. "Step 4 — about 3 more expected" beats a bar that sits at 80% for four minutes. If you cannot estimate, say so.

Show cost as it accrues when the user is paying. It is information they need in order to interrupt, and it does more for trust calibration than any amount of reassurance.

Trust calibration

Both directions are product failures.

Over-trust — the user accepts output without review, and errors flow through unchecked. Caused by uniformly confident presentation and by an early run of successes.

Under-trust — the user verifies everything, and the agent saves nobody any time. Caused by an early visible failure with no explanation, and by opaque behaviour.

The cure for both is the same: legibility. An agent that shows its work, cites its sources, expresses calibrated confidence, and says clearly when it is unsure lets a user learn when to trust it rather than whether to. Uniform confidence destroys that signal in both directions.

Undo, dry-run and preview as primitives

Design them in from the start; they are extremely hard to retrofit.

Dry-run — every mutating tool takes a mode parameter and can report what it would do. This is also your best debugging tool and your best demo.

Preview — show the diff before applying it. A file diff, a list of records to be changed, the draft email.

Undo — a compensating action for every mutating action, wherever possible. Where it is not possible, that fact should appear in the approval prompt as "this cannot be undone", because that is precisely the information the human needs.

Checkpoint and rewind — the whole session, not just individual actions. This is M5's session forking exposed to the user.

A useful reframing: turning an irreversible action into a reversible one is often cheaper than gating it. A soft delete with a 30-day retention window converts a rung-2 action into a rung-5 action, removes an approval from the human's day, and is usually a few hours of work.

The approve-all button

A product shipped per-action approval and users complained, so the team added "approve all for this session". Adoption was immediate and near-universal — clicked, on average, within the first ninety seconds of a session.

The product was now a fully autonomous agent, with an audit trail showing informed consent for every action. The approval flow had not been removed; it had been rendered ceremonial, and the ceremony made the risk harder to see rather than easier, because the logs looked impeccable.

What worked instead: risk tiering so only genuinely risky actions asked, batching for the rest, and scoped grants ("cache operations, this session") instead of unbounded ones. Approvals per session fell by roughly 80% and the remaining ones got read — median decision time went from 1.2 seconds to 9.
