The problem nobody warns you about

You build an agent. It works beautifully. You give it a longer task, and somewhere around turn twenty-five it starts getting worse — forgetting things you told it, ignoring earlier instructions, giving vaguer answers.

Nothing errors. Nothing in the logs looks wrong. The obvious conclusion is that the model got worse, or something is broken.

Neither. You ran out of attention.

The idea in one line

Every token you add is a token of attention you spend. Context is a budget, not a bucket.

Remember the context window from F1 — the model's desk, not its memory. Everything you send has to fit on that desk, and everything on the desk competes for the model's attention.

The window is large. It is not free. As it fills, the model's ability to reliably use any particular piece of it degrades.

It is a slope, not a wall

If you exceeded the window, you would get an error and you would know.

This is worse: performance falls off gradually. Recall gets patchier, early instructions lose their grip, the model leans on whatever is nearest the end. No error, no warning, no log line — your answers just get worse, and someone blames the model version.

What is actually in there

For a running agent, the window is usually filled roughly like this:

WhatTypical shareCan you shrink it?
Your instructions1–5%Rarely — small and load-bearing
Tool descriptions5–30%Yes — consolidate (M2)
The conversation5–15%Somewhat
What tools returned50–85%Yes — this is where the work is

Tool results dominate, and almost nobody guesses that. A file you read, a search result, a database query — each lands whole in the conversation and, because of how conversations work (F4), gets re-sent on every later turn. Turn 20 is still paying for the search result from turn 3.

That single fact decides your strategy. Polishing your instructions while tool results are 70% of the window is rearranging the furniture.

Writing instructions at the right height

Your instructions to the model — the system prompt — can fail in two opposite directions.

System prompt

Instructions sent with every request that set up who the model is and how it should behave. Separate from the conversation, and passed as system="..." in the API call.

Too specific is a pile of rules for every situation you have met. Brittle: the moment reality supplies a case you did not list, there is nothing to fall back on. It also grows forever, because every incident adds a rule.

Too vague is "be helpful, use good judgement". Nothing to act on, and no way for the model to know what your organisation considers correct.

What you want is a clear frame plus the specifics that are genuinely non-obvious:

Every line there is something the model could not have worked out. None of it is a flowchart.

That last line is F1 applied: the model will happily produce a plausible price from training. Making it look the price up is exactly the fix.

Examples beat rules

Three or four varied examples usually work better than a page of rules, and cost fewer tokens. An example carries tone, format and judgement all at once.

The word doing the work is varied. Four examples of the same easy case teach nothing. Pick the ordinary case, the ambiguous one, the one that must be escalated, and the one that looks in-scope but is not.

Fetch on demand instead of pre-loading

The instinct is to gather everything possibly relevant and send it all. For agents there is a better default.

Send a list of what exists, plus a tool to fetch any of it. Titles, identifiers, a one-line summary each. The model reads the list, decides which two matter, and asks for those.

This works because the model can see the shape of what is available without paying for the contents — and because a filename is itself information. 2026-q3-revenue-final.xlsx tells you something before you open it.

The result: the context ends up holding what was actually needed, rather than what you guessed might be.

Pre-loading still wins when there are only a handful of documents and all of them are relevant. Decide on purpose rather than by habit.

Three ways to handle long tasks

Eventually a conversation outgrows the window, or outgrows the point where the model handles it well. There are three answers, and mature agents use all three.

1. Summarise the old part

When the conversation gets long, replace the early turns with a summary and carry on.

The summarising instructions are the strategy. A generic "summarise this" loses exactly what the agent needs — which record it already updated, which approach it already ruled out — and it repeats work with no memory of having done it.

2. Keep notes in a file

The agent writes findings to a file outside the conversation, and reads them back when needed.

Cheap, readable by you during debugging, and it survives the program being killed — which makes it the basis of memory in M7.

3. Give the sub-task its own window

Hand a chunk of work to a separate agent with its own context. It reads twenty documents, burns 80,000 tokens, and returns two paragraphs. Your main conversation grows by two paragraphs.

The most powerful option and the most expensive — you are paying for a whole extra context. That is M9.

Paying less for the same text

There is one more lever, and it is nearly free.

Every turn re-sends the whole conversation (F4). Prompt caching lets the provider keep the unchanged front portion, so you are charged much less for re-sending it.

Prompt caching

The provider stores the beginning of your request. If the next request starts with exactly the same text, that part is reused and charged at roughly a tenth of the normal price.

It changes what you pay, not what is in the window. Attention is still spent.

The rule that matters: caching works on the beginning of the request, and the request is assembled in a fixed order — tools, then instructions, then conversation. Any change anywhere in that beginning throws away everything after it.

So: stable things first, changing things last.

The mistakes that quietly double your bill, roughly in order of how often they happen:

  • A timestamp in your instructions. "Current time: 2026-08-20T14:22:31Z" changes every request, so nothing ever caches. If the model needs the time, put it in the user's message instead.
  • Tools in a different order each run. Sort them.
  • Editing your instructions mid-conversation.
  • Switching model mid-conversation. Different model, different cache.
  • Adding or removing a tool mid-conversation. Tools come first, so this invalidates everything.

Notice the shape of all five: nothing fails, nothing warns, the bill just goes up. Watch cache_read_input_tokens. If it stays at zero across repeated calls, something in your prefix is moving.

"Just use the big context window"

Two runs of the same research task, both with plenty of room.

The first pre-loads forty documents, because it can. The second sends a list of forty titles and fetches the four it needs.

The smaller one wins on accuracy — the model's attention is not spread across thirty-six irrelevant documents — and it wins on speed and cost by a wide margin.

A large window is a safety margin, not a strategy. The question is never "does it fit". It is "does every token in here earn its place".

Letting the API manage context for you

Two features do some of this work server-side.

Context editing (beta header context-management-2025-06-27) removes old tool results rather than summarising them:

Given tool results are 50–85% of the window, clearing the stale ones is often the single highest-value change available.

Compaction (beta header compact-2026-01-12) summarises earlier context automatically as you approach a threshold. One catch that costs people hours: append the whole response.content back into your messages, not just the text. The compaction blocks are how the API knows what it already summarised, and pulling out only the text silently loses that.

What you now know

  • Context is attention, and it degrades gradually with no error.
  • Tool results are most of what fills the window, and they are re-sent every turn.
  • Instructions should be specific but not a flowchart; varied examples beat rule lists.
  • Fetch on demand rather than pre-loading — send identifiers, load what is needed.
  • Three long-task strategies: summarise, notes, separate windows. Choose with numbers.
  • Prompt caching cuts what you pay to re-send; anything changing near the front breaks it silently.
