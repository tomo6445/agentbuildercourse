Context is a budget, not a bucket

The window is large. It is not free. Every token you put in is a token of attention the model spends somewhere, and attention is finite in a way that storage is not.

The failure mode this produces is nastier than running out of space, because running out of space throws an error. This does not. Performance degrades gradually as context fills: recall gets patchier, instructions from early turns lose their grip, the model starts favouring whatever is nearest the end. Nothing raises. Nothing logs. Your evals drift down by a few points and someone blames the model version.

The idea in one line

Every token you add is a token of attention you spend. Context is a budget, not a bucket.

The practical stance: know what is in your window and why. Most engineers cannot answer that question about their own agent, which is why the Observatory gets a context-occupancy view in this module.

What actually occupies the window

For a long-running agent the breakdown is usually something like:

ComponentTypical shareCompressible?
System prompt1-5%Rarely — it is small and load-bearing
Tool definitions5-30%Yes, via consolidation and tool search
Conversation turns5-15%Somewhat
Tool results50-85%Yes — this is where the work is

Tool results dominate, and almost nobody's mental model says so. A file read, a search result, a database query, an API response — each lands whole in the transcript and is re-sent on every subsequent turn. Turn 20 pays for the search result from turn 3 again.

That single fact determines the strategy. Optimising your system prompt when tool results are 70% of the window is rearranging deck chairs.

System prompt altitude

There is a right height to fly at, and both extremes fail.

Too low is hardcoded logic: sprawling if-then rules for every situation you have encountered. Brittle, and it fails the moment reality supplies a situation you did not enumerate. It also grows without bound, because every incident adds a rule.

Too high is vague encouragement — "be helpful", "use good judgement". Nothing to act on, and it gives the model no way to know what your organisation considers correct.

Examples compress better than rules

Three or four diverse, canonical examples routinely outperform a page of rules, because an example carries tone, format, edge-case handling and judgement all at once, in fewer tokens.

The word doing the work is diverse. Four examples of the same easy case teach nothing. Pick examples that span the space: the ordinary case, the ambiguous one, the one that must escalate, the one that looks in-scope but isn't.

Just-in-time retrieval

The reflex from RAG systems is to pre-load: gather everything possibly relevant, stuff it in, let the model sort it out. For agents there is a better default.

Carry identifiers, load on demand. Instead of pasting five documents into context, give the agent a list of what exists — titles, ids, one-line summaries — and a tool to fetch any of them. The model reads the list, decides which two matter, and loads those.

This works because the model can see the shape of the corpus without paying for its contents, and because a file path or a row id is itself information: 2026-q3-revenue-final.xlsx tells you something before you open it. It also means the agent's context reflects what it actually needed rather than what you guessed it might.

Progressive disclosure is the same idea one level up, and it is exactly how skills work in M14: always-loaded name and description, body when relevant, referenced files on demand.

Classic pre-loading still wins when the corpus is small and every document is relevant, or when latency matters more than tokens and you can afford the round trips saved. Decide deliberately.

The three long-horizon strategies

Eventually the transcript outgrows the window, or outgrows the point where the model reasons well over it. There are three answers, and mature agents use all three.

Compaction

At a threshold, summarise the conversation so far and continue from the summary plus the most recent turns.

The summarisation prompt is the strategy. A generic "summarise this" loses exactly the things the agent needs — which record it already updated, which approach it already ruled out — and the agent repeats work it has no memory of having done.

The API can also do this server-side: compaction (beta header compact-2026-01-12) summarises earlier context automatically as you approach a threshold. If you use it, append the whole response.content back into your messages, not just the text — the compaction blocks are how the API knows what it already summarised, and extracting only text silently loses that state.

A lighter-weight relative is context editing (beta context-management-2025-06-27), which clears old tool results rather than summarising them: context_management={"edits": [{"type": "clear_tool_uses_20250919"}]}. Given that tool results are 50-85% of the window, clearing the stale ones is often the highest-value single change available.

Structured note-taking

The agent maintains a file outside the context window and reads it back when it needs to.

Cheap, legible, debuggable, and it survives process death — which makes it the foundation of memory in M7. The discipline it needs is hygiene: notes that only grow become their own context problem.

Sub-agent isolation

Give the sub-task its own context window. The sub-agent explores, reads twenty documents, burns 80,000 tokens, and returns a two-paragraph finding. The orchestrator's context grows by two paragraphs, not by eighty thousand tokens.

This is the most powerful of the three and the most expensive. It is also the whole subject of M9, where you will find that the token multiple is real and the quality gain has a knee.

Prompt caching as context economics

Caching does not reduce what is in your window. It reduces what you pay to re-send it — often by an order of magnitude — which changes which designs are affordable.

The mechanic that matters is that caching is a prefix match. The request renders in a fixed order — tools, then system, then messages — and any byte that changes anywhere in the prefix invalidates everything after it.

Which gives you the rule: stable content first, volatile content last.

The mistakes that silently cost you real money, in rough order of how often they happen:

  • A timestamp in the system prompt. "Current time: 2026-08-19T14:22:31Z" invalidates the cache on literally every request. If the model needs the time, put it in the user turn.
  • Non-deterministic tool ordering. A tool list built from a set or a dict iteration that varies between processes. Sort it.
  • Editing the system prompt mid-session to add an instruction. On supporting models, append a {"role": "system", ...} message to messages[] instead — the cached prefix survives, and it is the injection-safe channel for operator instructions.
  • Switching models mid-session. Different model, different cache. Use a sub-agent for the cheap sub-task instead of switching the main loop.
  • Adding or removing tools mid-session. Tool search appends definitions rather than swapping them, which is precisely why it preserves the cache.

Note the shape of every one of those: nothing fails, nothing warns, the bill just goes up. Watch usage.cache_read_input_tokens. If it is zero across repeated requests, something in your prefix is moving.

“Just use the big context window.”

Two runs of the same research task, both with room to spare. The first pre-loads forty documents because it can. The second carries a list of forty titles and loads the four it needs. The smaller-context run wins on accuracy — because the model's attention is not spread across thirty-six irrelevant documents — and it wins on latency and cost as well, by a wide margin. A large window is a safety margin, not a strategy. The question is never "does it fit", it is "does every token in here earn its place".
