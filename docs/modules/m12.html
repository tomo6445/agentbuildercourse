Build the model

Cost per task decomposes into five terms:

The term that surprises people is the first, and specifically how it grows. On turn n you re-send the entire transcript. Across a task of n turns, history tokens accumulate as n(n−1)/2 — quadratic, not linear. A 20-turn task does not cost twice a 10-turn task. It costs roughly four times.

This single fact reorders every optimisation you might attempt. Halving your turn count beats halving your model price.

This instrument needs JavaScript. The lesson reads fine without it.

Prices change, so treat them as inputs rather than constants. Check the current published rates, put them in one config, and make your cost model read from it. As a rough shape at the time of writing: Haiku-class models sit around a dollar per million input tokens, Sonnet-class around three, Opus-class around five, with output at roughly five times input — and cache reads roughly a tenth of the input price. Verify before quoting.

Prompt caching in earnest

Caching is the highest-leverage cost lever available and it is nearly free to adopt. The mechanics from M3, applied with intent:

Order for a stable prefix. Requests render tools → system → messages. Everything stable goes first, everything volatile last.

Place breakpoints deliberately. You get up to four. Typically: end of tools, end of system prompt, and a rolling one in the conversation. Below roughly 1,024 tokens a prefix will not cache at all — silently.

Verify. usage.cache_read_input_tokens is the only honest signal. Zero across repeated requests means something is moving.

The changes that silently double your bill, all of which pass code review:

ChangeWhy it breaks the cache
A timestamp in the system promptPrefix differs on every single request
Tool list built from a set or dictOrder varies between processes
Appending an instruction to system mid-sessionThe prefix changed; use a {"role":"system"} message instead
Switching model mid-sessionDifferent model, different cache
Adding or removing a tool mid-sessionTools render first; use tool search, which appends
A per-request ID early in the promptSame as the timestamp

Every row is invisible in testing and expensive in production. Put cache hit rate on a dashboard (M10) so a regression is a graph, not a quarterly surprise.

Model routing

Not every step needs your best model. Classification, extraction, simple formatting and much judging run well on a small model; planning and synthesis need a strong one.

Two disciplines make routing safe rather than merely cheap:

A quality floor. Route cheap, then measure with your M8 suite per route. A route that drops below its floor gets promoted back. Without this, routing is just a way to make your product worse for money.

Don't switch mid-session. Changing model in the middle of a conversation invalidates the cache and can cost more than the model saved. Spawn a sub-agent for the cheap sub-task and keep the main loop on one model.

Also consider the Batch API for anything not latency-sensitive — overnight evals, bulk classification, backfills. Roughly half price for work nobody is waiting on.

Latency

The thing people get wrong: agent p95 is dominated by turn count, not per-turn speed.

A 400ms improvement per turn is 400ms on a one-turn task and meaningless against a task that sometimes takes 25 turns. The tail is made of runs that took many more turns than the median, so the levers that matter are:

  • Fewer turns. Tool consolidation (M2) removes round trips wholesale.
  • Parallel tool execution. Independent calls concurrently — the M1 lesson, and still the most common avoidable latency in production agents.
  • Streaming. Does not reduce latency; substantially reduces perceived latency, which is what users report on.
  • Prefetching. If a tool is almost always called first, call it before the model asks.
  • A turn cap tuned from data. The p99 run that takes 40 turns is usually thrashing, not working.

Reliability under statefulness

Stateless services taught us that a failed request is retried and forgotten. Agents are not stateless, and the same fault has very different consequences.

A crash on turn 18 of a 20-turn task loses eighteen turns of work and the money spent producing them. Do it under load and you have an outage that is also a bill.

Checkpoint after every turn. Messages, tool state, budget spent, memory pointers. Resumption should be the normal recovery path, not an exotic one.

Make tool calls idempotent, or make them safe to repeat. If a resumed agent re-issues send_email, an idempotency key is the difference between a resume and an incident.

Durable execution. For long-running agents, a workflow engine that persists state transitions lets a worker die mid-task and another pick it up. The alternative — restart from zero — becomes untenable exactly when tasks become valuable.

Design tool errors an agent can recover from. M2's lesson with money attached: an error that says what is wrong and what to try instead converts a failed run into a degraded one.

The retry storm

Naive retries turn a blip into an outage, and they do it in a way that looks locally reasonable.

Rate limit hits. Every in-flight agent retries immediately. The retries arrive together, are also rate-limited, and retry again. Now you have more load than the original traffic, sustained, with the provider's limiter guaranteeing every one of them fails — and each retry re-sends a full transcript, so the bill grows while the success rate is zero.

And the third: a budget guard that aborts the run when spend crosses the ceiling, regardless of what the retry logic thinks it is doing. Retries are how a bug becomes expensive; the budget guard is what bounds the damage.

Graceful degradation and budget policy

Decide in advance what happens when a limit is hit. There are three answers and they are product decisions, not engineering ones:

  • Degrade — finish with a cheaper model, fewer workers, or a partial answer clearly marked as partial.
  • Escalate — hand to a human with the work so far attached.
  • Abort — stop and report honestly.

Whichever you choose, say it out loud in the Decision Log, and set budgets per session, per tenant and per task. A per-session cap does not stop one tenant consuming everything.

Rainbow deployments

The constraint stateless services never taught you: you have agents mid-task during a deploy.

Kill a pod and you kill a 20-turn task at turn 12. Multiply by concurrent load. A rolling deploy that is invisible for a web service is a mass-cancellation event for an agent fleet.

Rainbow deployments shift traffic gradually and let old versions keep running until their in-flight work completes. New tasks go to the new version; existing tasks finish where they started. It costs you running two versions concurrently for a while, which means both must tolerate the same session format — a compatibility constraint worth knowing about before you need to change that format.

The retry storm

An intermittent 429 from a downstream API. The client retried three times with no jitter. Two hundred concurrent agents hit the limit within the same second, all retried at t+1s, all failed, all retried at t+2s.

Sustained load rose to roughly six times baseline for eleven minutes. Every retry re-sent a full transcript — averaging 40,000 tokens — so the bill for that window ran to four figures with a 0% success rate. The dashboard showed nothing unusual until the invoice, because the agents were "working": no errors surfaced to users, just slow tasks that eventually gave up.

Fixed with jittered exponential backoff, a circuit breaker on the downstream service, and a per-session budget guard that aborts rather than retries into a wall. The alert that would have caught it in minutes is cost per task, p95 — the first metric in M10's list.
