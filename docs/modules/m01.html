The Loop: what an agent actually is

An agent is a while-loop with a language model in it. Everything else is ergonomics.

The idea in one line

An agent is a while-loop with a language model in it. Everything else is convenience.

That is not a simplification for beginners. It is what an agent is, and people who have built them for years would agree. The rest of this course is about doing each of those three steps well — which turns out to be where all the difficulty lives.

Agent

A program that lets a language model decide what to do next, carries out those decisions, and feeds the results back — repeatedly, until the job is done.

The word gets used loosely in marketing. In this course it means precisely the loop above.

From one call to a loop

In F4 you made a single call. You sent a question, got an answer, and the program ended.

That is useful, and it is limited: the model can only tell you things. It cannot look anything up, check anything, or do anything. It is answering from what it absorbed during training, which is exactly the situation where it invents libraries that do not exist (F1).

An agent fixes this by giving the model a way to ask your program to do things. Those things are called tools.

Tool

Something your program can do, described to the model in words so it knows the option exists.

A tool might look up the weather, search a database, read a file, or send an email. You write the code that does the work. You also write the description that tells the model when to use it.

You will hear "function calling" for the same idea. Same thing.

The round trip, slowly

Here is one complete cycle. Read it twice — everything else in this module is detail on top of it.

1. You send a message, and a list of the tools that exist.

2. The model replies asking for a tool to be used.

Not with an answer — with a request. Inside response.content you now find a block like this:

Read it as: "please run the thing called get_weather, with city set to Oslo, and label the answer toolu_01A9FqvKbT7X so I know which request it belongs to."

3. Your program runs it. You look up get_weather among your functions and call it. It returns something like "4C, light rain".

4. You send the result back. You add the model's request and your result to the conversation and call the API again — exactly like the back-and-forth in F4, because that is exactly what this is.

5. The model uses the result to answer.

"It's 4°C and lightly raining in Oslo."

That is the whole mechanism. Now the crucial part.

The model does not run anything

This is the single most important idea in the module, and the vocabulary works against you. "Tool calling" and "function calling" both suggest the model reaches out and runs something.

It does not. It cannot. The model produces text (F1). A tool_use block is a piece of text shaped like a request. It has no more power than any other thing the model writes.

Your code is what turns that text into an action.

Once you see it, several things follow that would otherwise be baffling:

  • The model can ask for a tool that does not exist. It is generating plausible text, and a plausible tool name is easy to generate. Your program has to cope.
  • The model can ask for a tool with wrong or missing information.
  • The model can ask for something the user never authorised.

This is where safety actually lives

If you write "never delete files" in your instructions to the model, that is a request. The model will usually honour it, and "usually" is not a guarantee.

If your program refuses to run anything called delete_file, that is a rule. It holds regardless of what the model asks for or what any document it read told it to do.

Module 11 is entirely about this distinction. For now: any time you think "the model shouldn't do X", ask what happens when it does.

Writing it

Here is the loop. It is longer than the countdown from F3, but every piece is something you know: a while loop, an if, a for loop over a list, and dictionaries.

Walk through it once with the round trip above in mind. Ask, check whether it is done, record the request, run the tools, report back, repeat.

The part that runs one tool

try / except

A way to run code that might fail without your whole program stopping.

Python attempts the try part. If it fails, it runs the except part instead and carries on. Here it means a broken tool produces a message rather than killing the agent mid-task.

function(**block.input) is a shortcut: it takes the dictionary {"city": "Oslo"} and calls function(city="Oslo"). The two stars unpack the dictionary into named values.

Four rules that will bite you

These are not style preferences. Three of them are enforced by the API, and the fourth costs you money quietly.

Every request needs a matching result. Each tool_use block has an id. Your result must carry the same id in tool_use_id. Miss one and the API rejects the whole message.

Send the model's turn back exactly as it came. response.content, unmodified. Do not rebuild it by hand.

Problems come back as results, not crashes. An error inside a tool_result lets the model read it and try something else. A crash ends the run. That one line is the difference between an agent that recovers and one that falls over.

All results go in one message. If the model asks for three tools, all three results go in a single messages.append(...). Splitting them works, and quietly teaches the model to stop asking for several things at once — which shows up weeks later as an agent that got mysteriously slower.

Knowing why it stopped

response.stop_reason tells you why the model stopped writing. You must branch on this rather than guessing from what came back.

stop_reasonWhat it meansWhat your loop does
end_turnFinished its answerStop; return the text
tool_useWants one or more toolsRun them, send results, continue
max_tokensHit your length limit mid-sentenceNot a finished answer — handle it
pause_turnA long-running built-in tool pausedSend the turn back to resume
refusalIt declined the requestDo not treat the content as an answer

The trap is max_tokens. A truncated reply contains no tool_use blocks, so code that asks "are there any tool requests?" concludes the agent is finished and hands the user half a sentence as though it were the answer.

Check the reason, not the contents

Making it stop

Look again at while turns < 10. That limit is doing serious work.

Remember the infinite loop from F3 — the one you stopped with Ctrl + C. An agent can do the same thing, except each time around it costs money and there may be nobody watching.

There are three ways it happens:

It retries something that will never work. A tool is broken; the model tries again; nothing in the conversation says "this is permanently broken", so it tries again. And again.

It goes back and forth forever. Two tools that point at each other — one says "results may be stale, verify", the other says "re-check the source". The model bounces between them making no progress.

It drifts. Nothing errors at all. It starts on the question you asked, finds something adjacent and interesting, and forty turns later delivers a good answer to a different question.

A turn limit catches all three, bluntly. But turns are a rough proxy for what you actually care about, which is money:

Two limits, checked before each call, so an exhausted budget never buys one more turn. This is the cost_of function you wrote in F3, doing a real job.

"The model deleted my files"

It didn't. Something more interesting happened, and the distinction is the whole module.

The model produced a tool_use block naming a delete function. That is ordinary text — the same kind of thing as "the capital of Norway is Oslo". The API returned success. Nothing was broken.

Then a program — written by a person, on purpose — looked up that name, found a real function, and ran it.

Every point where you might have stopped it is in your code: the lookup that could have refused, the check that could have asked a human, the sandbox that could have made the file unreachable. None of those is in the model.

The same reasoning applies to a tool name that does not exist, which happens constantly. Your program looks it up and finds nothing. If it crashes, the run dies with a stack trace nobody asked for. If it returns an error saying which tools do exist, the model reads it, apologises, and picks a real one. Same model, same question, completely different product — and the difference is about six lines you control.

Seeing what happened

When an agent does something strange — and it will — "it gave a weird answer" is not something you can debug. You need to see what actually happened: which tools ran, what came back, how many turns, what it cost.

So the agent writes down every turn as it goes:

Trace

A record of what an agent did, step by step. Sometimes called a log.

The word "trace" suggests something you can follow — which is the point. You are not looking for one error message; you are following a sequence of decisions to find where it went wrong.

In the second lab you turn that list into a web page you can read. It will be ugly. It does not matter — you extend it in eleven of the remaining fifteen modules, and by the end you will be reading agent behaviour rather than guessing at it.

Writing the trace properly

The version above is fine to start. Two fields are worth adding now, because retrofitting them later is annoying.

A @dataclass is a shortcut for making a class that mostly holds values: Python writes the boilerplate for you. str | None means "text, or nothing".

cache_read_tokens is how you discover in M3 that your prompt cache stopped working — a problem whose only symptom is a larger invoice. And recording stop_reason on every turn is how you spot a run that ended on max_tokens and was reported to a user as a complete answer.

Who runs what

One last distinction, because it changes what you are responsible for.

Tools you write — the weather lookup, the database query — run on your machine, in your process. You own the code, the speed, the failures, and the security.

Built-in tools — web search, running code in a sandbox — run on Anthropic's servers. You declare them and results come back without passing through your program at all.

That difference matters more than it first appears: a built-in tool never goes through your lookup function, so any check you put there does not see it. If an action needs your permission logic, it has to be a tool you wrote.

What you now know

  • An agent is a while loop that asks a model what to do, does it, and reports back.
  • Tools are things your program can do, described to the model in words.
  • The model never runs anything. It emits a request; your code acts. Safety lives in your code.
  • Every request needs a matching result, all results go back in one message, and errors come back as results rather than crashes.
  • Branch on stop_reason, not on what the reply happens to contain.
  • Loops must be made to stop: turn limits and budget limits, checked before each call.
  • A trace is how you find out what actually happened.
