The interface nobody designs

We spend careers on human-computer interfaces — affordances, error messages, undo, progressive disclosure. Then we expose a language model to eight functions named get_data, do_thing and process, with no parameter descriptions, and conclude from the resulting mess that the model is bad at our domain.

An agent-tool interface is a user interface. Its user reads only text, has no memory of your codebase, cannot ask a colleague, and must decide from the description alone whether this is the right tool for what it is trying to do. It deserves the same care as a human interface and typically gets a fraction of it.

Anatomy of a tool definition

Three fields. The third is a schema; the second is a prompt.

Read that description again as though you were the model. It answers four questions, in order:

  1. What does it do? Search customers by name, email or account number.
  2. When should I reach for it? Whenever you need a customer ID — and it tells you the negative space too: no other tool takes a name, so this one is the entry point.
  3. What comes back? Named fields, so the model can plan its next turn instead of guessing.
  4. What does failure look like? Empty is not an error. Without that sentence, models routinely report "the customer does not exist" after a single narrow query.

Most tool descriptions in the wild answer only the first, in six words.

The hidden tax

Tool definitions are not free and they are not paid once. They occupy context on every turn of every conversation, whether the tool is used or not, and enabling tools at all adds a system-prompt surcharge on top.

Concretely: forty tools averaging 300 tokens each is roughly 12,000 tokens per turn, before the user has typed anything. On a fifteen-turn task that is 180,000 tokens of pure definition — more than most tasks need in total. This is a bill and a context-budget problem at the same time, and it is the single most common way an MCP integration (M6) quietly ruins an agent.

Three consequences follow:

  • Every tool must earn its slot. "It might be useful someday" is a cost you pay per turn.
  • Description length is a real trade-off. Longer descriptions genuinely improve selection accuracy, up to a point. Pay for the sentences that change behaviour; cut the ones that restate.
  • Prompt caching changes the arithmetic, not the principle. A cached tool block is much cheaper to re-send, but it still occupies attention. Caching fixes the invoice, not the context rot.

Consolidation beats coverage

The instinct from API design is to mirror the backend: one tool per endpoint, CRUD for everything. It produces a tool surface shaped like your database and nothing like the tasks users have.

Consider a calendar integration exposed as list_events, get_event, create_event, update_event, delete_event, list_attendees, add_attendee, check_availability. To schedule a meeting the model must chain five of them, each round trip adding latency, tokens and a chance to go wrong.

Replace them with one tool shaped like the actual job:

One call instead of five. Fewer turns, less context, fewer failure points, and — critically — the tricky logic (availability intersection, name resolution, fallback slots) lives in your code where it is testable, instead of being improvised by the model across five round trips.

The rule of thumb: name tools after tasks, not after tables. If a tool's name is a verb from your ORM, look again.

Namespacing and the thirty-tool wall

Prefix by system: crm_search_customers, calendar_schedule_event, github_open_pr. This costs a few tokens and buys three things — no collisions when you add a second integration, an obvious grouping the model can reason about, and the prerequisite for tool search later.

Somewhere around thirty tools, "add another tool" stops working. Selection accuracy degrades before context does: the model is choosing from a menu too long to hold clearly in mind, and near-duplicates start attracting each other's calls. The fixes, in order of how much they change your architecture:

  • Consolidate. Most large tool sets are a small number of tasks fragmented across many endpoints.
  • Split by agent. Give each sub-agent (M9) only the tools its job needs.
  • Tool search. Mark tools defer_loading: true and add a search tool (tool_search_tool_regex_20251119 or the BM25 variant); the model retrieves the definitions it needs. Definitions are appended rather than swapped, so the prompt cache survives. Never defer every tool — the search tool itself and at least one other must stay loaded.

Poka-yoke: making the wrong call hard

Poka-yoke is the manufacturing practice of designing parts that cannot be assembled wrongly. Apply it to parameters.

Closed sets become enums. A status parameter typed as a free string invites "cancelled", "CHURNED", "inactive" — three ways to be wrong. As an enum, the wrong value is a schema error you never see rather than a silent empty result.

Opaque identifiers say where they come from. "customer_id" with no description gets invented. "The customer_id returned by crm_search_customers" gets looked up.

Booleans that switch behaviour become named modes. force=true is a coin flip. mode with ["dry_run", "apply"] is self-documenting, and the safe value is the one whose name says what it does.

Structured objects over parallel arrays. Two arrays that must line up by index will, eventually, not line up.

Use strict tool use for the ones that matter. Setting strict: true on a tool definition (with additionalProperties: false and a required list) guarantees the arguments validate against your schema exactly — turning a class of malformed-argument bugs into something the API enforces rather than something your handler discovers.

Returns and errors are prompts too

Whatever a tool returns becomes context the model reasons from. Shape it deliberately.

Resolve identifiers to names. Returning {"owner_id": "u_8823fa"} forces another round trip or, worse, an invented name. Return {"owner": "Dana Ruiz", "owner_id": "u_8823fa"} and the model can write the sentence immediately.

Return what is needed, not what is available. A row with forty columns when the task needs three is thirty-seven columns of attention spent for nothing, on every subsequent turn.

Paginate with intent. Say how many results exist, how many were returned, and exactly how to get the next page. "Showing 10 of 47 matches. Call again with page=2 for the next 10." — the model now knows both that more exist and precisely what to do about it.

Never truncate silently. A tool that quietly cuts a 48,000-token document to 4,000 and returns it unmarked produces confident, false answers with no error anywhere in the trace. If you truncate, say so in the payload: "[truncated: showing 4,000 of 48,000 tokens; call with offset=4000 to continue]".

Make errors instructive. Compare:

UnhelpfulInstructive
Error: invalid inputError: 'status' must be one of active, churned, trial, any (got 'cancelled').
Error: not foundNo customer matches 'j.smith'. Try a broader query, or search by account number.
Error: 500The CRM is unavailable for scheduled maintenance until 14:00 UTC. No lookup will succeed this session — tell the user and stop retrying.

That last one is the one people miss. An error that tells the model retrying is futile is the difference between a graceful stop and the error thrash you simulated in M1.

“The model is bad at this.”

Six real cases where a team concluded the model could not handle their domain. In every one, the model was doing exactly what the tool layer told it to. A get_records whose description was "gets records" — selected almost at random against its three neighbours. A date parameter with no format specified — nine different formats emitted across a hundred runs. A search that returned [] on no-match with no explanation — reported to users as "that customer doesn't exist" instead of retried. A limit with no maximum documented — 5,000 rows requested, context blown. In the lab you rewrite each description and watch the failure disappear without touching the agent.

Working with Claude on your tool layer

Here is a workflow that feels like cheating and is standard practice: give the failing transcripts to Claude and ask it to diagnose the tool layer.

You have the eval failures, the tool definitions, and the traces. Paste them in and ask which tool descriptions caused which failures, and what the rewrite should say. The model is unusually good at this, for the obvious reason that it is the reader you are writing for. It will flag ambiguities you cannot see because you know what you meant.

Do this after your own analysis, not instead of it, and treat the output as a proposal to test — the eval set stays the judge.

Lab 2 — Tool surgery

labs/lab02_tool_surgery gives you eight deliberately-flawed CRM tools, a 20-task eval set, and a harness that runs it. One rule: only the tool layer may change. The agent loop, the system prompt and the eval set are frozen.

Baseline is roughly 55% pass rate. Get to 85% or better while reducing total tokens. The tests check both, so you cannot buy accuracy with a thousand-word description.
