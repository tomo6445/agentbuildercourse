The thing that kills most agent projects

Most agent projects do not die of a hard technical problem. They die like this: somebody makes a change, nobody can tell whether it helped, so changes stop being made — and the thing that worked in the demo keeps not working in reality for reasons nobody can name.

The idea in one line

If you cannot measure it, you cannot improve it, and you should not ship it.

This is the module that M4's fifth question pointed at. It is also the least glamorous thing in the course and the one most correlated with a project surviving.

Why this is harder than normal testing

Ordinary code is easy to test: given this input, expect exactly that output. Run it twice, get the same answer.

Agents break every one of those assumptions.

They take many steps. A failure at turn 12 might be caused by something at turn 4.

They vary. The same question can produce different routes on different runs. One run tells you almost nothing.

Earlier choices constrain later ones. Two runs that both failed may have failed for unrelated reasons.

Several good answers exist. Often more than one route reaches an equally good result. A test demanding one specific route punishes correct behaviour — and whoever is trying to make the number go up will simply delete that test.

They touch real systems. Your tests need an environment that is stable enough to compare against and realistic enough to be worth comparing.

Two questions, not one

Did it get the right answer? Necessary. Not sufficient.

Did it get there sensibly? Did it use the tools it should have, avoid the ones it shouldn't, stay within a reasonable number of turns, and not do anything alarming on the way?

You need both, and here is why. Imagine a question with two plausible answers, where one tool distinguishes them. The agent skips the tool, picks one at random, and happens to be right.

Checking the answer only: pass. Checking the route: it never called the tool that decides.

That agent will be wrong tomorrow, and an answer-only test just certified it as fine.

Start with twenty cases

The most common reason a team has no tests is that they are waiting until they can build good ones. Do not wait.

Twenty real cases — from actual usage, actual questions, actual complaints — is enough to catch the failures that matter. The first batch of problems is usually systematic rather than subtle, and you do not need statistical rigour to find a systematic bug. You need examples.

How to choose them:

  • Take them from reality, not imagination. Your imagination produces the case that works.
  • Cover three difficulties. Easy ones catch things breaking. Normal ones are the real distribution. Hard ones should sometimes fail — that is your headroom.
  • Include the ones you are nervous about. The ambiguous request. The one where the right answer is "I don't know". The one that should be handed to a human.
  • Include cases that should be refused. If nothing in your set rewards the agent for saying "I can't answer that", you will train that behaviour out of it.

Then grow the set from real failures. Every incident becomes a permanent case. That is the flywheel.

Using a model as the grader

For anything open-ended you cannot check the answer with a simple comparison, so you use a model to grade it. This works, and it fails in specific documented ways.

The ways graders go wrong

They reward length. Longer, more fluent answers score higher regardless of substance.

They punish honesty. An answer saying "the sources do not cover this" gets marked incomplete — so you train the honesty out.

Order affects them. In head-to-head comparisons, position matters.

They favour their own family. A model grading output from its own family scores it higher.

Check the grader before trusting it

An unchecked grader is a random number generator with good manners

Before you believe a single score:

  1. Hand-label 30 outputs yourself, against the rubric, before seeing the grader's labels.
  2. Run the grader on the same 30.
  3. Compare — and not just by counting matches.
  4. Read every disagreement. The grader is usually right about something you under-specified.
  5. Fix the rubric. Re-measure. Repeat.

Step 3 needs care, because raw agreement lies. On a set where 80% of cases pass, a grader that passes everything agrees with you 80% of the time and is worthless.

Cohen's kappa

A number that corrects agreement for luck. It asks: how much better than chance is this?

1.0 is perfect. 0.0 is no better than guessing. Above about 0.6 is usually considered solid.

A grader that passes everything scores well on raw agreement and gets a kappa of 0.0 — which is why this is the number to look at.

And the rule that has to be stated because the temptation is genuine: when the grader and your labels disagree, you fix the rubric, never the labels. Adjusting your reference answers to match the grader produces a test suite that agrees with itself and nothing else.

Reading transcripts yourself

Sit down and read fifty runs. Not summaries — the actual transcripts.

You will find things no automated check was looking for, because automated checks only test what somebody thought to assert.

The well-known example: an agent whose answers were factually correct and properly cited, passing every check, which had quietly learned to prefer low-quality content farms over authoritative sources — because the farms were easier to extract clean quotes from. No dimension for source quality existed until a human noticed. Then it became one, and stayed caught.

Budget for this before every significant change.

Running tests automatically

A test suite that runs when somebody remembers is not a control.

CI

Continuous Integration. A service that runs your tests automatically whenever code changes, and blocks the change if they fail.

For agents it needs four things ordinary CI does not.

Handle the variation. Run each case several times and judge on the aggregate. A single flaky failure must not block a merge — and a case passing 2 times in 5 is failing, even though it is green sometimes. Report pass rates, not pass/fail.

Cap what the test run itself can spend. A test suite that can spend without limit is its own incident.

Decide what blocks. Easy cases must be 100% — any failure there is a regression. Normal cases block below a threshold. Hard cases are reported but never block, or people will delete them to get green.

Track cost and turns as results. A change that keeps accuracy and doubles cost is a regression. If your tests only report accuracy, that regression ships.

That last one gets left out. An agent that is right 90% of the time, consistently, is a product. One that averages 90% by being excellent on Mondays and useless on Tuesdays is a support burden — and the average hides it completely.

The 95% agent that failed in production

Passing 95% in testing, visibly bad in the real world.

The test set had been written by the team, from memory, in an afternoon. So it encoded the questions they expected: well-formed, unambiguous, answerable from one document, phrased the way an engineer phrases things.

Real users asked compound questions, referred to things not in the documents, phrased things ambiguously, and often wanted answers the sources could not support. The agent had never been tested on saying "I don't know", so it did what it had been optimised to do: answer confidently.

The fix was procedural. Take test cases from actual logs, deliberately including the messy, the ambiguous and the unanswerable — and add every production failure as a permanent case.

Feeding failures back for improvement

Give the failing transcripts to a model along with your tool definitions and instructions, and ask what went wrong and what to change. It is remarkably effective, for the same reason as in M2: it is the reader you are writing for.

The trap is over-fitting. Iterating against the same twenty cases eventually produces a system tuned to those twenty cases and nothing else.

Guard it: hold back cases the improvement loop never sees, refresh the set from real usage regularly, and treat a suspiciously large jump as evidence that answers leaked into the tuning rather than as success.

Lab 8 — measure it

labs/lab08_evals has you validate a grader and catch injected regressions.

The naive rubric scores 75% raw agreement and kappa 0.50 — and fails on exactly two cases: one citing a content farm, and one correctly abstaining. Adding those two dimensions takes it to kappa 1.00, with no other change.

Then three regressions your suite must catch. One keeps every answer correct and stops calling the tool — invisible to answer-only testing, which is the point.

What you now know

  • Agents are hard to test: many steps, variable, path-dependent, several valid routes.
  • Check the answer and the route. Answer-only testing passes the agent that got lucky.
  • Twenty real cases beats waiting for a perfect set. Include hard, ambiguous and unanswerable ones.
  • A model grader needs a rubric with named dimensions — it will not apply standards you did not write.
  • Check the grader against your own labels, using kappa rather than raw agreement. Fix the rubric, never the labels.
  • Read transcripts yourself. Automated checks only find what somebody thought to assert.
  • Run tests automatically with pass rates, a spending cap, and cost tracked as a result.
