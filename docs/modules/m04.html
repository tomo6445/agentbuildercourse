The most common mistake in this field

You now know how to build an agent. The next thing to learn is when not to.

The idea in one line

The most common architectural mistake is reaching for an agent when simpler code would do.

That sounds like caution. It is not — it is what the measurements say. In this module's lab you build the same task six ways, and the simple arrangement matches the agent's accuracy at a fifth of the cost, with a more predictable response time.

The reason people get this wrong is social, not technical. "Agentic" has become a word that means "good", so the simple version feels like settling. Meanwhile the simple version is faster, cheaper, easier to test, and easier to explain to whoever gets paged when it breaks.

The actual distinction

A workflow: your code decides what happens next. You wrote the steps. The model does the parts that need language.

An agent: the model decides what happens next — which tool, in what order, for how many turns — based on what it finds.

Workflow

A program where the sequence of steps is written by you in code, and a model is used for particular steps within it.

Not a lesser thing than an agent. A different tool, and usually the right one.

The line is not sophistication. It is who chooses the path. A three-model workflow with careful handoffs is not more primitive than a one-model agent; it is a different answer to a different question.

The five arrangements

You will build all five in the lab. Descriptions are cheap; the numbers you get from building them are the point.

1. Chaining — fixed steps in order

Use it when the steps genuinely are fixed. Each step gets a prompt tuned for one job, and you get natural places to put ordinary checks.

2. Routing — sort first, then handle

This is the pattern most teams should have used and didn't. Each route gets instructions tuned for one thing instead of a compromise prompt covering everything, each can be tested separately, and the easy majority can go to a cheaper model without touching the hard cases.

3. Doing things at once

Two shapes.

Splitting — independent pieces done simultaneously. Forty documents; five aspects of one document. Total time drops to the slowest piece.

Voting — the same work done several times, then compared. Useful when you need confidence on a judgement call, and disagreement between the runs is itself a signal worth surfacing.

4. A lead with helpers

A lead model breaks the task up, hands pieces out, and combines what comes back. The difference from splitting is that the pieces are not known in advance — the lead works them out from the input.

This is the multi-agent pattern. It gets its own module (M9), mostly because of what it costs.

5. Draft and critique

Works when you can state the quality criteria clearly and a second pass genuinely improves things — translation, writing to a style guide, code against a specification.

It fails expensively when the criteria are vague: the critic generates plausible objections forever. Always cap the rounds. The loop must stop on a budget, not on satisfaction — the same lesson as M1's turn limit, in a new costume.

And the agent

Beyond all five sits the thing you built in M1: open-ended, unpredictable number of steps, deciding as it goes.

It earns its place when the path genuinely cannot be listed in advance — an unfamiliar codebase, an open research question, debugging. A good test: could a competent person write the steps down before starting? If they could not either, that is a real agent problem.

What autonomy costs

Autonomy is something you buy. Here is the price, so you can decide whether you want it.

You getYou pay
Handles cases you did not anticipateTime: unpredictable step count, often 5–20× a single call
Recovers from surprisesMoney: the whole conversation re-sent every turn (M3)
No flowchart to maintainMore ways to fail: every turn is a chance to go wrong
Improves as models improveHarder debugging: "why did it do that" has no stack trace
One implementation covers many casesHarder testing: many valid paths make "correct" hard to define

None of those means never build an agent. They are the reasons to be able to say out loud why this task needs one.

Five questions

Answer these in writing before you build. They take twenty minutes and save weeks.

1. Can you list the steps in advance? If you can draw the flowchart, build the flowchart.

2. Does each step depend on what earlier steps found? A single decision up front is routing. Deep, repeated dependence is where agents start to pay for themselves.

3. Is one completed task worth more than the compute? A run costing $0.50 is fine for a task worth $50 and absurd for one worth 5 cents. Do this arithmetic before building.

4. Can the actions be undone? Irreversible actions do not forbid autonomy, but they change the design — dry runs, approval steps (M13), a smaller blast radius.

5. Can you tell automatically whether it worked?

Question 5 is a veto, not a trade-off

The first four are judgement calls you can make either way.

This one is not. If you cannot tell whether a run succeeded, you cannot improve it, cannot catch it getting worse, and will find out it is broken when a user tells you.

If the honest answer is no, the work in front of you is building a way to measure it (M8) — not building the agent. An agent you cannot measure is not a prototype. It is a liability with a good demo.

"Agentic" used to mean "good"

Three projects, same shape.

A document-classification pipeline rebuilt as an agent: six times the cost, four times the wait, and worse accuracy — because the old pipeline's per-step prompts had been tuned and the agent's general-purpose prompt had not.

An internal search tool given a full agent loop when a single retrieval answered 90% of queries. The extra turns mostly re-searched what turn one already found.

A data-entry automation where the flexibility became the bug: it "helpfully" corrected values the customer had deliberately entered.

In all three, nobody had asked question 1.

Combining the patterns

Real systems mix these. A support product might route first, then use chaining inside the billing route, and reserve a full agent for the small fraction of tickets that need investigation.

The useful habit is to apply the five questions per class of work rather than to the product as a whole. "Does this need an agent?" usually has different answers for different parts of the same system, and the expensive mistake is picking one answer for everything.

This is the same move you will make in M13 for autonomy levels, and for the same reason.

What you now know

  • Workflow: your code chooses the path. Agent: the model chooses.
  • Five arrangements: chaining, routing, doing things at once, a lead with helpers, draft and critique.
  • Routing is the one most teams should reach for first.
  • Any loop that stops on satisfaction rather than a budget will not stop.
  • Autonomy costs time, money, failure surface, debuggability and testability.
  • If you cannot measure success, do not build the agent yet.
