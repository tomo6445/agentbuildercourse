The patterns are the same

By now you have the whole vocabulary: workflows and agents, tool design, context strategy, memory, evaluation, multi-agent, observability, security, cost. Eight domains follow, and the striking thing is how little the architecture varies.

What varies enormously is what kills you. Every domain punishes a different mistake, and the mistake is usually not the one your instincts are guarding against.

The idea in one line

The patterns are the same. The failure modes are not.

Software engineering

Architecture: autonomous agent · file and shell tools · checkpointing · test-gated loop.

The canonical agentic domain: the path genuinely cannot be enumerated, feedback is immediate and machine-readable, and errors are cheap in a branch.

What bites you: verification. "It compiles" is not "it works", and an agent optimising for a green build will produce a green build. Without a test gate you get plausible code that passes review and fails in production.

Do: make tests the loop's success criterion, not a step in it. Check out to an isolated worktree. Checkpoint per turn — long tasks and crashes are routine. Never let the agent modify the tests it is being graded by, which it will do, sincerely, given the chance.

Research and analysis

Architecture: orchestrator-workers · wide parallel search · synthesis with citations.

The domain where multi-agent genuinely pays (M9): parallelisable, read-heavy, and valuable enough to absorb the multiple.

What bites you: source quality. Agents drift toward SEO content farms, because they are optimised to be extractable — clean structure, quotable sentences, confident phrasing. The output looks excellent and is sourced from nothing.

Do: put source quality in the rubric explicitly (M8). Give explicit heuristics — prefer primary sources, prefer the filing over the article about the filing. Require a citation per claim and assert it in evals. Surface conflicts rather than averaging them.

Data and business intelligence

Architecture: routing plus SQL tools · read-only credentials · validation before execution.

What bites you: schema hallucination and silent wrong answers. A query against a misremembered column name errors, which is fine. A query with subtly wrong join semantics returns a plausible number, which is not. Nobody checks a number that looks reasonable.

Do: read-only credentials, always. Provide the schema as a resource rather than hoping it is remembered. Validate queries before execution. Add sanity checks — row counts, totals against known aggregates, order-of-magnitude assertions. Show the query alongside the answer, every time: it is the only way a human can catch this class.

Customer operations

Architecture: routing workflow with an escalation ladder · policy retrieval · tight scope.

Rarely a full agent. Routing plus specialised handlers is faster, cheaper and far more predictable at volume.

What bites you: confident wrongness at scale. One wrong answer is a ticket; the same wrong answer delivered five thousand times before anyone notices is a regulatory problem.

Do: scope tightly and escalate aggressively — the correct action is often "hand to a human". Require a citation to a specific policy document for anything consequential. Monitor for distribution shift in the answers themselves, not just in volume. Make abstention a rewarded outcome in your evals (M8), or you will optimise it away.

Document processing

Architecture: prompt chaining plus evaluator-optimiser · per-field confidence · human review queue.

What bites you: the long tail and silent truncation. 95% of documents match the format you tested. The remaining 5% is unbounded — scans, rotated pages, tables spanning page breaks, handwriting — and the failure is a confidently extracted wrong value, not an error.

Do: per-field confidence, and route low-confidence fields to human review rather than guessing. Never truncate silently (M2). Sample the tail deliberately when building the eval set; the tail is where your accuracy actually lives.

DevOps and SRE

Architecture: narrow, high-privilege tools · dry-run first · approval on mutations · exhaustive audit.

What bites you: blast radius. These agents hold the most dangerous tools in any domain, and the lethal trifecta (M11) lives here by default: private data (infrastructure state, secrets), untrusted content (logs, alerts, tickets, third-party status pages), and egress (the ability to change production).

Do: dry-run everything by default; apply is a separate, gated mode. Approval on every mutation (M13) — this is the domain where rung 2 is correct. Audit everything durably. Narrow the tools: restart_service(name) not bash. And write the threat model down, because this is the domain where someone will eventually inject a log line on purpose.

Sales and CRM

Architecture: MCP-heavy integration · memory for account context · write validation.

What bites you: data hygiene and PII. An agent with write access to a CRM can degrade it faster than a team can repair it — duplicates, malformed fields, overwritten human notes. Meanwhile customer records are exactly the private data leg of the trifecta.

Do: validate every write against the schema and against existing records. Deduplicate before creating. Never overwrite a human-authored field — append. Run a redaction hook on every result (M5), because CRM data will otherwise end up in your traces, logs and evals.

Personal and internal automation

Architecture: scheduled agents · narrow scope · self-reporting.

The domain that looks easiest and has the worst failure mode.

What bites you: unattended failure nobody notices. A nightly agent breaks in week one and "succeeds" silently for three weeks. Nobody is watching, because the entire point was not to have to watch.

Do: alerting and self-reporting are the design, not additions to it. Report every run, including successful ones, so silence is itself an alarm. Assert on outputs, not just exit codes. Set a dead-man's switch: no run in 26 hours pages someone. And put a hard budget cap on it, because an unattended agent in a retry loop is unattended for a long time.

Deployment shape

Two broad shapes, and the choice is usually made by constraints rather than preference.

Self-hosted harnessManaged Agents
You operateEverythingThe client
ControlTotalConfiguration surface
ComplianceData stays where you put itGoverned by the provider's terms
Long-runningYou build resumption, schedulingSessions, scheduled deployments
SandboxYou build and harden it (M11)Hosted per-session container
Best whenStrict data residency, custom runtime, existing infraYou want the loop and the sandbox operated for you

The compliance question usually decides it. The latency question rarely does; the control question is often overstated until the first time you need to change something the configuration surface does not expose.

Same architecture, four domains, four different deaths

The same orchestrator-workers system, adapted four times.

In research, it died on source quality — beautifully synthesised, sourced from content farms. In BI, it died on a join: a plausible number, wrong, acted on for a month. In document processing, it died on the 5% tail — the eval set was built from the documents that were easy to collect, which were the ones that parsed. In DevOps, it died on blast radius: a dry-run flag that defaulted to false.

Four teams, four architectures they could each defend, four failures none of them was watching for. Pattern literacy told them how to build it. Only domain literacy told them what to fear — and that comes from the failure catalogue of the domain, not from the architecture diagram.
