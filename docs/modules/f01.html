The one-sentence version

A language model reads some text and predicts what text should come next.

That is genuinely it. Everything else — the helpfulness, the code, the analysis, the occasional confident nonsense — comes out of that single ability, applied at enormous scale.

The idea in one line

It predicts the next piece of text. Everything surprising about it follows from that, in both directions.

It is worth sitting with how strange that is. Nobody programmed the model with rules about Python syntax or French grammar or how to write a polite refusal. It was shown an enormous quantity of text and trained to predict what comes next, over and over. The capabilities we care about turned out to be consequences of getting very good at that.

This explains the two things beginners find most confusing:

Why is it so capable? Because predicting the next word well, across billions of examples, requires actually modelling a great deal about how the world and language work. To finish the sentence "The capital of Norway is ___" you need to know something.

Why does it confidently say false things? Because it is producing text that looks like what should come next — and plausible-looking text is not the same thing as true text. We will come back to this, because it matters enormously once the model can take actions.

Tokens: the unit of everything

A model does not read letters or words. It reads tokens.

Token

A token is a chunk of text — very roughly ¾ of a word in English. Common words are usually one token each. Longer or unusual words get split into several.

"The cat sat on the mat" is about 6 tokens. "Antidisestablishmentarianism" is about 7 tokens on its own.

You will see this word constantly for the rest of the course. It is the unit models read in, write out, and — importantly — the unit you are charged for.

Three practical consequences, and you should hold on to all three:

You pay per token, in both directions. Text you send in costs money. Text the model writes back costs money, usually several times more per token. When we start counting costs in Module 12, this is the arithmetic.

There is a limit to how much it can hold at once. This is the context window.

Everything is text. The document you paste, the instructions you give, the reply it writes — all the same kind of stuff, all tokens. This sounds like a technicality. It becomes a security problem in Module 11, and it is the single most important thing on this page.

Context window

The maximum number of tokens the model can consider at one time — everything you sent it plus everything it writes back. Current Claude models can hold roughly a million tokens, which is a very large book.

Think of it as the model's desk, not its memory. Whatever is on the desk right now is what it can work with.

What the model can see, and what it cannot

This trips up nearly everyone, so let us be precise.

When you send a message, the model sees exactly what you sent it, and nothing else. It does not remember your last conversation. It cannot look at your files. It has no idea what happened yesterday. It is not connected to anything.

"But it remembered what I said earlier in the chat!" It did — because the chat application quietly re-sent the whole conversation with your new message. Every single time. The model did not remember; the software around it re-reminded it.

That is worth restating, because the entire course depends on it:

The model is stateless

Each call starts from nothing. Any sense of memory, continuity or ongoing work is created by the software around the model re-sending the relevant history every time.

When you build an agent, you are that software. Deciding what to re-send is your job, and it turns out to be one of the hardest and most expensive decisions you will make. That is Module 3.

Why it makes things up

The model produces text that looks like what should come next. Usually, text that looks right is right — that is why it works at all. But the mechanism does not have a step where it checks whether something is true.

So when you ask about something obscure, or something that does not exist, you often do not get "I don't know". You get a confident, well-formed, completely fabricated answer — because a confident well-formed answer is what looks like what comes next.

The classic version, which you will hit personally within a week of writing code:

You ask for code that solves a problem. It writes something clean and sensible that imports a library called easyparse. The code is well-structured. The function names are good. The library does not exist and never has.

This is not the model being broken. It is the model doing exactly what it does — producing plausible text — in a case where plausible and true came apart.

What follows from this, practically:

  • Anything factual and important gets checked. Always.
  • Prefer designs where the model looks something up rather than recalls it. This is a large part of why agents exist at all, and it is Module 2.
  • The confidence in the writing tells you nothing about the accuracy of the content. Nothing. A fabricated answer and a correct one are written in exactly the same tone.
Why "hallucination" is a slightly misleading word

The term suggests a malfunction — the model glitching. It is closer to the opposite: the model is working precisely as designed, and the design has no truth-checking step in it.

A more useful frame is that the model is always doing the same thing, and the question is whether the plausible continuation happens to be accurate. For well-covered topics it almost always is. For obscure ones it often is not, and the model has no internal signal telling it which situation it is in.

This is why the fix is architectural rather than a matter of asking more nicely. You give the model a way to check, and you verify the important things yourself.

The model versus the product

One more distinction, because the vocabulary is genuinely confusing.

The model is the thing that predicts text. On its own it does nothing at all — it cannot browse, remember, run code or send email.

The product is the software wrapped around it. When you use Claude in a browser, you are using a product: it manages the conversation, re-sends history, may search the web, renders the output nicely.

An agent — the thing this whole course is about — is another kind of software wrapped around the model. It gives the model a way to request actions, performs those actions, and feeds the results back. That loop is Module 1, and by the end of Phase 0 you will have built one yourself.

Prompt

The text you send to the model. That is all it means.

You will hear "prompt engineering" used as though it were arcane. It mostly means: being specific, giving examples, and saying what you actually want. It matters, and it is not mystical.

Try this before moving on

Genuinely do this — twenty minutes, and it will make the next three modules land much better. Open Claude (or any chat assistant) in your browser and try all four:

  1. Ask something it knows well. "Explain how a bicycle gear changes work." Note how good it is.
  2. Ask something obscure and checkable. A detail about a small local business, a minor historical figure, a specific page of a specific book. Then check it. Notice the tone is identical whether it is right or wrong.
  3. Ask it what you said three messages ago. It will tell you. Now remember that it only knows because the app re-sent the whole conversation.
  4. Ask it something it cannot possibly know — what is on your desk, what time it is where you are. Watch what it does with a question it has no access to answer.

Those four experiments are the whole of this module, in a form you cannot forget.

What you now know

  • A language model predicts what text comes next. Everything follows from that.
  • It reads and writes tokens, which is what you are billed for.
  • It has a context window — a desk, not a memory.
  • It is stateless. Continuity is created by software re-sending history.
  • It produces plausible text, and plausible is not the same as true.
  • The model, the product, and an agent are three different things.
