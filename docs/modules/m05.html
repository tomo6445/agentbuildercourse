Adopting someone else's loop

You wrote the loop in M1. Now the honest question: should you keep it?

Usually not. Other people have written this loop, handled the awkward cases, and given you sessions, permissions and cost tracking for free. But adopting a framework without understanding it is how you end up unable to debug anything — which is exactly why we did M1 first.

Four options

Two separate questions decide this, and mixing them up is why the choice confuses people:

Who writes the loop? and whose computers does it run on?

Your own loop is what you built. Keep it when you need control the others do not offer.

Tool Runner is part of the ordinary Anthropic library. It runs the loop over tools you write:

That replaces your entire M1 run() function. The tool description is generated from the docstring — which means everything in M2 now applies to your docstrings.

Decorator

The @beta_tool line above a function. It is a marker that hands your function to something else to modify or register.

Read @beta_tool as "treat this function as a tool". You do not need to know how they work to use them.

Managed Agents is the only option where Anthropic runs both the loop and the computer the tools execute on. Good when you want long-running, resumable, scheduled agents without operating any of it.

Claude Agent SDK is a different product — Claude Code as a library. It comes with tools for reading and writing files, running shell commands and searching, plus permissions and sessions.

Tool Runner is not the Agent SDK

They sound alike and are unrelated packages.

Tool Runner is a small helper in the normal API library. It loops over tools you write and ships none of its own.

Claude Agent SDK is a separate package with built-in file and shell tools.

Both run on your machine. Only Managed Agents runs on Anthropic's. Getting this wrong sends people hunting for filesystem tools in the wrong library for an afternoon.

The honest way to adopt a framework is to know which of your lines it is deleting.

Everything in the left column still exists. You are now debugging someone else's version of it — which is fine, because you know what it is supposed to be doing.

Sessions: not starting over

Your M1 agent kept the conversation in a variable. Close the program and it is gone.

A session saves it, so a crash at turn 30 is a resume rather than a lost hour.

Session

A saved conversation, stored somewhere that survives the program stopping — a file or a database.

Save after every turn. The moment you want it is exactly the moment you cannot create it.

Branching, which is the real trick

The underused capability is forking: take a saved conversation, branch it at turn 14, change one thing, and run both.

That is a controlled experiment, and it is the only reliable way to answer questions like:

  • Did the new tool description fix it, or did the run just come out differently?
  • Was it the summarising step, or the tool result just before it?

Without it, you re-run whole tasks and compare outcomes that vary anyway, which needs many runs to say anything. With it, you change one thing. M10 builds its whole debugging approach on this.

Permission rules

A permissions layer decides, per tool call, whether to allow it, refuse it, or ask a human.

Genuinely useful. Now understand exactly what it is not.

A rule is a gate, not a wall

A rule matching bash commands containing curl is doing text matching on input an attacker may control. The same action can be written /usr/bin/curl, $(which curl), a variable, a base64-encoded blob piped into a shell, or four lines of Python opening a network connection.

Every deny-list is a claim that you thought of all the spellings. You did not.

Permission rules are worth having: they catch mistakes, which is most of what actually happens, and they give a human a place to intervene. They stop a determined attacker only by luck. For that you need a boundary the program cannot talk its way around — a machine with no network access, a filesystem that does not contain the secrets. That is M11.

The lab makes you prove this on your own rules, which is more convincing than being told.

Hooks: your code at fixed points

A hook runs code you wrote at a defined moment — before a tool runs, after it returns, when a session starts.

Hook

A place where the framework stops and runs your function, letting you inspect or change what is happening.

"Before every tool call, run this." "After every result, run that."

Four things they are genuinely good for:

Checking before running. Refuse a write outside the working folder; refuse an email to an outside address when policy says internal only.

Removing sensitive information from results before they enter the conversation — which also keeps it out of your logs and your saved traces, where it otherwise leaks from.

Recording everything. Every tool call, its arguments, and what happened. Do this from day one. It costs nothing and is the difference between explaining an incident and shrugging.

Stopping on cost.

Decide in advance what hitting a ceiling does — degrade, escalate to a human, or stop. Working that out at 3am is worse.

Hooks are policy, not protection

A team put personal-data removal in a hook and called the system compliant. The hook cleaned results from the tools it knew about.

Then somebody connected another integration. Its tools did not match the hook's patterns, and unredacted customer records began leaving the building through a path the compliance review had already approved.

A hook that asks nicely is a policy. Policies belong in hooks. Actual protection belongs in the network and the filesystem, where nothing can route around it.

Lab 5 — port and harden

labs/lab05_sdk_port has you build the harness pieces yourself in plain Python — permissions, hooks, sessions — so you can see what the abstraction does before letting it do it.

The test worth reading is test_a_permission_gate_is_not_a_sandbox. It tries five ways of reaching the network past your own rules. Two are caught. Three are not — and none of those three contains the word the rule was looking for.

What you now know

  • Four options: your own loop, Tool Runner, Managed Agents, Claude Agent SDK. Two questions separate them: who writes the loop, and whose computer it runs on.
  • Tool Runner ≠ Agent SDK. Different packages, different scope.
  • A session is a saved conversation. Save every turn; a crash becomes a resume.
  • Forking a session lets you change one thing and compare — a real experiment.
  • Permission rules catch mistakes. They are not protection against someone trying.
  • Hooks run your code at fixed points: checking, redacting, logging, stopping on cost.
