Four ways to build an agent

You have written the loop. Now decide what to ship. Two independent questions separate the options: who supplies the harness (the loop plus context management) and who supplies the deployment (the infrastructure it runs on). Conflating those two is why this choice confuses people.

You writeHarnessDeploymentTools
Manual loopThe whole loopYouYouOnly yours
Tool RunnerJust the tool functionsSDKYouOnly yours
Managed AgentsAgent config + your tool resultsAnthropicAnthropicHosted sandbox + Skills/MCP + yours
Claude Agent SDKA prompt + optionsSDK (Claude Code)YouRead/Write/Edit/Bash/Glob/Grep/Web + MCP + subagents

The manual loop is what you built in M1. Keep it when you need control the runner does not expose, or when you cannot take a beta dependency.

The Tool Runner is part of the regular Anthropic SDK — client.beta.messages.tool_runner with @beta_tool-decorated functions. It drives the loop over tools you define. No built-in tools, no sandbox; you still host everything.

That replaces your entire M1 run() function. The schema is generated from the signature and docstring — which means the docstring is now the tool description, and everything in M2 applies to it.

Managed Agents is the only option that supplies both the harness and the deployment: Anthropic runs the loop and hosts a per-session container where bash, file operations and code execution happen. Agents are persisted, versioned objects; sessions reference them. Reach for it when you want long-running, resumable, scheduled agents without operating any of it.

The Claude Agent SDK is a different product — Claude Code packaged as a library (claude-agent-sdk). It ships the full harness plus built-in file, shell, search and web tools, hooks, permissions, subagents and sessions. You call it with a prompt and options and it drives everything, on infrastructure you provide.

Tool Runner is not the Agent SDK

They sound alike and are unrelated packages. Tool Runner is a thin helper over POST /v1/messages for your own tools. The Agent SDK is the Claude Code harness with built-in tools. Both leave deployment to you; only Managed Agents adds hosted deployment. Getting this wrong sends people looking for filesystem tools in the wrong library.

Everything in the left column still exists. You are now debugging someone else's version of it, which is exactly why you wrote yours first.

Sessions, and forking as a debugging superpower

Sessions persist a conversation so it can be resumed after the process dies — which turns "the agent crashed on turn 30" from a lost hour into a resume.

The underused capability is forking. Take an existing session, branch it at turn 14, change one variable, and run both branches. Same history, same state, one difference.

This is a controlled experiment, and it is the only reliable way to answer questions like:

  • Does the new tool description actually fix the misselection, or did the run just vary?
  • Is this failure caused by the compaction, or by the tool result that preceded it?
  • Would a cheaper model handle turns 15-30 as well?

Without forking you are re-running whole tasks and comparing stochastic outcomes, which needs many samples to say anything. With forking you change one thing. Fold this into your habits now; M10 builds replay-driven debugging on top of it.

Permissions: a gate, not a sandbox

A permission layer decides, per tool call, whether to allow, deny, or ask. Typical policy:

This is genuinely useful and you should use it. Now understand precisely what it is not.

A permission rule matching on command patterns is doing string analysis on an adversarial input. curl can be /usr/bin/curl, $(which curl), a shell variable, a base64 blob piped to sh, or a Python one-liner that opens a socket. Every deny-list is a claim that you enumerated the ways to express an action, and you did not.

Deny-lists are also the wrong shape. An allow-list of permitted operations fails closed; a deny-list of forbidden ones fails open, and it fails open in exactly the cases you did not think of.

The real boundary is the one the process cannot talk its way past: a sandbox that cannot reach the network, a filesystem mount that does not contain the credentials, a proxy that only resolves allow-listed domains. That is M11, and this is the module that tells you why you need it.

Hooks as a security boundary

A team put PII redaction in a pre-tool hook and called the system compliant. The hook redacted arguments to the tools it knew about. Then someone added an MCP server, whose tools did not match the hook's patterns, and unredacted records started leaving the building through a path the compliance review had already approved. A hook that asks nicely is a policy, not a control. Policies belong in hooks; controls belong in the network and the filesystem.

Hooks

Hooks run your code at lifecycle points — before a tool call, after it, at session start, on completion. Four things they are genuinely good for:

Validation. Reject a call before execution: a write_file outside the working directory, a send_email to an external domain when the policy is internal-only.

Redaction. Strip secrets and PII from tool results before they enter context — which also stops them entering your traces, your logs and your evals.

Audit. Append every tool call, argument and outcome to a durable log. Do this from day one. It costs nothing and is the difference between an incident you can explain and one you cannot.

Budget enforcement. Accumulate cost per session and abort when the ceiling is hit. Deciding in advance whether hitting a ceiling degrades, escalates or aborts is a design decision; discovering it at 3am is not.

Structured output and cost tracking

When a downstream system consumes the agent's answer, you need a shape, not prose. Use output_config.format to constrain the response to a schema — and prefer client.messages.parse(), which validates for you.

Two notes that will save you an afternoon. Assistant prefills — the old trick of seeding the response with { to force JSON — return a 400 on current models; structured outputs replace them. And output_config.format is incompatible with document citations, so if you need both, get citations into your schema as fields instead.

For cost, read usage off every response and accumulate: input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens. The cache fields are not optional detail — they are how you learn your cache broke (M3) and they are the dominant term in most agent cost models (M12).

Lab 5 — Port and harden

labs/lab05_sdk_port moves your M3 research agent onto a harness. Required:

  • two custom tools, ported from your M1 registry
  • disk-persisted sessions that resume after the process is killed mid-task
  • a permission policy that denies network writes, with a test proving the denial
  • three hooks: pre-tool validation, PII redaction on results, and a cost-ceiling abort
  • schema-conformant structured output

The gate is deliberately harsh: your M3 eval suite must pass unchanged. A port that quietly changes behaviour is not a port. Then the new tests — resume-after-kill, cost-ceiling abort, permission denial — must also pass.
