- Say what several agents actually buy you, which is not what most people think
- Recognise the tasks where it pays and the tasks where it burns money
- Write instructions precise enough that helpers do not duplicate each other
- Decide how many helpers from the shape of the task rather than by habit
- Combine conflicting findings without inventing a confident wrong answer
- Find the point where adding another helper stops being worth it
:::

## What it actually buys you

The usual pitch is specialisation: a research agent, a writing agent, a critic. That framing is
mostly wrong — a single model with good instructions plays all three perfectly well.

The real benefit is **separate context windows**.

Remember from M3 that everything an agent reads stays in its conversation and gets re-sent every
turn. A helper with its own window can read twenty documents, burn 80,000 tokens exploring, and hand
back two paragraphs. Your main conversation grows by two paragraphs.

::: key
Not "the researcher is better at researching", but "the researcher's mess stays in the researcher's
window".
:::

::: jargon Orchestrator and workers
The **orchestrator** (or lead) is the agent that decides how to split the task, hands pieces out, and
combines what comes back. **Workers** (or subagents) are separate agents that each do one piece.

Each worker is a complete agent as built in M1 — its own loop, its own conversation, its own tools.
:::

And the price, plainly: **several times the tokens of a single agent.** You are paying for a whole
extra context per worker.

::: key
Several agents can cost many times a single one. The task has to be worth it.
:::

## When it pays

On wide searching — where the work is finding and reading a lot of material — how much you can read
largely determines how well you do. More parallel context is then directly more capability.

Three conditions, and **all three** must hold:

- **The work splits.** Genuinely independent pieces, not a chain where step 2 needs step 1's answer.
- **It is mostly reading.** Gathering and filtering, not a sequence of changes to something.
- **It is worth the multiple.** The value of one completed task can absorb several times the cost.

## When it fails

**They do each other's work.** Two workers with overlapping instructions run nearly the same
searches and hand back nearly the same findings. You paid twice for one result. This is the most
common failure, and it is an instructions problem rather than a code problem.

**They disagree.** Worker A says 2.1B, worker B says 2.15B. Now the lead has to decide — and its
instinct is often to average them or pick the better-written one, both of which are wrong.

**Coordinating costs something.** Splitting up, waiting, and combining all take turns and tokens.
Below a certain size the overhead exceeds the benefit and one agent doing it directly is faster and
better.

**One slow worker holds everything up**, and one hung worker stalls the lot.

## The instructions are the hard part

This is where these systems are actually built or lost. A vague brief produces overlapping,
uncitable, unusable findings, and no amount of clever coordination recovers from it.

A worker's instructions need five things:

```text
TASK: Find the FY2025 revenue figure for Acme Corp and the year-on-year change.

SCOPE: Revenue only. Do NOT look into margins, headcount, competitors or
       outlook — other workers are covering those. If you come across
       something relevant outside your scope, note the source and move on.

TOOLS: search, fetch_document. You may not write files or send anything.

EFFORT: This is a single-fact lookup. Expect 2-4 searches. Stop once you have
        a figure from a primary source; do not keep looking for more
        confirmation beyond two independent sources.

OUTPUT: JSON with keys: figure, yoy_change, sources (each with url, quote,
        date), confidence (high/medium/low), caveats.
```

**Say what the others are doing.** That SCOPE line is what stops duplication. Without it, every
worker helpfully investigates the interesting adjacent thing.

**Restrict tools per worker.** A read-only worker should be read-only in configuration, not by
request. This is also a security control (M11): a worker reading untrusted web pages should not be
holding tools that write.

**Say how much work this is worth.** Without a stated expectation, a worker runs until it feels
finished — and for a model on an open-ended search, that is a long way out.

**Demand a fixed output shape.** The lead has to combine these. Prose does not combine.

**Require confidence and caveats.** They give the lead something to work with when findings
conflict, instead of guessing.

## How many workers

A fixed number is how you end up with eight agents on a question one lookup answers, and one agent on
a question needing twenty. Put the rule in the lead's instructions:

```text
Choose how many workers from the shape of the task:

  a single fact, one source        -> 1
  comparing N things               -> N workers, one each, up to 6
  open-ended research              -> 5-10, split by sub-question
  a survey with a known list       -> one per item, batched, up to 12

Never exceed 12. If it seems to need more, the split is wrong — do two rounds
instead.
```

## Combining is the lead's hardest job

Everything so far was preparation for this. The lead now holds several findings and must produce one
answer.

**Decide conflicts by a rule you set in advance.** Prefer primary sources over secondary. Prefer
recent over old *for things that change*. Prefer higher confidence when sources are equally good.

**When a conflict cannot be resolved, say so.** *"Sources disagree: the annual report says 2.1B, the
press release says 2.15B"* is a far better answer than a confident average.

**Keep the citations.** The lead is rewriting text, and rewriting is exactly when attributions get
dropped. Require sources to survive into the final answer, and test for it.

::: warn Three confident workers can be confidently wrong together
Three workers return the same wrong figure. The lead combines them into a fluent, well-organised,
entirely false answer — because agreement reads as confirmation.

The structure **amplified** the error rather than catching it.

Defences: require a source for every claim, have the lead check whether the workers actually used
*independent* sources, and treat unanimous confidence on a hard question as suspicious rather than
reassuring.
:::

::: autopsy Two workers, same search, twice the bill
Two workers, briefed "research the competitive landscape" and "analyse market positioning".

A person reads those as different questions. The workers ran seventeen searches between them,
thirteen of them identical, and returned findings that overlapped by about 80%.

The fix was not in code. It was a line in each brief naming what the *other* worker was covering,
plus a shared list of what had already been searched. Duplicate searches dropped to two, with no loss
of quality.

That generalises: nearly every efficiency problem in these systems is an instructions problem, and
the instinct to fix it with coordination code is an instinct to fix it in the wrong place.
:::

::: deeper Failing gracefully when a worker dies
A worker that crashes or hangs must not take the run with it. Have failures come back as a marker
rather than an exception:

```python
def run_worker(brief):
    try:
        return worker(brief)
    except Exception as problem:
        return Finding(topic=brief.topic, value=None, failed=True,
                       note="worker failed: " + str(problem))
```

Then the lead's combining step reports what it could not cover:

> *"Revenue and outlook confirmed. Margin could not be established — that worker failed."*

A partial answer that says what is missing is worth far more than a crash, and it is worth more than
a complete-looking answer with a silent hole in it.

Same idea as M1's rule that errors come back as results rather than crashes, one level up.
:::

## The decision rule

Before you build one, all three must be true:

1. **It splits** into genuinely independent pieces.
2. **It is mostly reading**, not a sequence of changes.
3. **It is worth the multiple.**

If not, a single agent with good context management (M3) will be cheaper, faster and far easier to
debug.

## What you now know

- The benefit is **separate context windows**, not specialisation.
- It costs **several times** a single agent. All three conditions must hold: splits, mostly reading,
  worth the multiple.
- **Instructions are where these systems are won or lost.** Say what others are covering.
- **Restrict tools per worker**, in configuration.
- **Say how much effort** the task is worth, and choose worker count from its shape.
- Surface conflicts rather than averaging. Keep citations. Treat unanimity on hard questions as a flag.
