## The distinction that matters

**Workflows** orchestrate models and tools through predefined code paths. You wrote the control
flow; the model fills in the steps.

**Agents** let the model direct its own process — deciding which tools to use, in what order, for how
many steps, based on what it finds.

The line is not sophistication, it is **who decides the path**. A three-model workflow with careful
prompt chaining is not "less advanced" than a one-model agent. It is a different, usually better,
answer to a different question.

::: key
The most common architectural error in this field is reaching for an agent when a workflow would do.
:::

The reason this error is so common is social rather than technical. "Agentic" has become a synonym
for "good", so the workflow feels like the compromise. Meanwhile the workflow is faster, cheaper,
more predictable, easier to evaluate, and easier to explain to the person who has to be on call for
it.

## The five workflow patterns

You will implement all five in the lab against one problem. Descriptions are cheap; the numbers you
get from building them are the point.

### 1. Prompt chaining

Decompose into fixed steps, each feeding the next, with optional programmatic gates between.

```python
def chain(client, brief):
    outline = ask(client, "Write an outline for this brief.", brief)
    if len(outline.split()) < 30:                  # a gate, in code
        return {"status": "rejected", "reason": "outline too thin"}
    draft = ask(client, "Write the piece from this outline.", outline)
    return {"status": "ok", "text": ask(client, "Tighten and fix errors.", draft)}
```

Use it when the steps genuinely are fixed. You trade latency for accuracy on each subtask, and you
get a natural place to put deterministic checks.

### 2. Routing

Classify the input, then dispatch to a specialised handler.

```python
ROUTES = {"billing": handle_billing, "technical": handle_technical,
          "account": handle_account, "other": handle_general}

def route(client, ticket):
    kind = classify(client, ticket, labels=list(ROUTES))   # cheap model, one call
    return ROUTES[kind](client, ticket)                    # specialised prompt + tools
```

Routing is the pattern most teams should have used and didn't. Each route gets a prompt tuned for
one thing rather than a compromise prompt for everything, each is separately evaluable, and you can
send the easy 80% to a cheaper model without touching the hard 20%.

### 3. Parallelisation

Two distinct shapes.

**Sectioning** splits a task into independent pieces run concurrently — process forty documents,
review five aspects of one document at once. Latency drops to the slowest section.

**Voting** runs the *same* task several times and aggregates. Use it when you need confidence on a
judgement call: three independent reviews of a code change catch more than one review does, and
disagreement is itself a signal worth surfacing.

### 4. Orchestrator-workers

A lead model decomposes the task dynamically, delegates to workers, and synthesises. The difference
from sectioning is that the subtasks are **not known in advance** — the orchestrator decides them
from the input.

This is the multi-agent pattern, and it earns a whole module (M9) mostly because of what it costs.

### 5. Evaluator-optimiser

One model produces, another critiques against explicit criteria, loop until it passes or the budget
runs out.

```python
def evaluate_optimise(client, task, max_rounds=3):
    draft = generate(client, task)
    for _ in range(max_rounds):
        verdict = critique(client, draft, CRITERIA)   # returns {passed, notes}
        if verdict["passed"]:
            return draft
        draft = revise(client, draft, verdict["notes"])
    return draft                                      # budget exhausted, return best effort
```

It works when you can articulate the criteria clearly and when a critique genuinely improves the
next draft — translation, writing with a style guide, code against a spec. It fails, expensively,
when the criteria are vague: the critic generates plausible-sounding objections forever. **Always cap
the rounds.** The loop must terminate on a budget, not on satisfaction.

## The autonomous agent

Beyond all five sits the agent proper: open-ended, unpredictable step count, environmental feedback
in the loop, running until it decides it is done or you stop it.

It earns its place when the path genuinely cannot be enumerated — an unfamiliar codebase, an
open-ended research question, a debugging session. The tell is that a competent human doing this task
would also not be able to list the steps in advance.

## The price list

Autonomy is a purchase. Here is what it costs, so you can decide whether you want it.

| You gain | You pay |
| --- | --- |
| Handles cases you did not enumerate | Latency: unpredictable step count, often 5-20× a single call |
| Recovers from unexpected failures | Tokens: the whole transcript re-sent every turn, growing quadratically |
| No flowchart to maintain | Error surface: every turn is a chance to go wrong, and errors compound |
| Improves as models improve | Debuggability: "why did it do that" has no stack trace |
| One implementation for many cases | Evaluability: many valid paths make correctness hard to assert |

None of those are reasons never to build an agent. They are the reasons to be able to say, out loud,
why this task needs one.

## A decision framework you can reuse

Five questions. Answer them in writing, in your Decision Log, before you write code.

**1. Can you enumerate the steps in advance?** If you can draw the flowchart, build the flowchart.

**2. Does the next step depend on what earlier steps discovered?** Shallow dependence is routing.
Deep, repeated dependence is where agents start to pay.

**3. Is the task worth more than the compute?** An agent run that costs $0.50 is fine for a task
worth $50 and absurd for one worth $0.05. Do this arithmetic before building, not after rollout.

**4. Are the actions reversible?** Irreversible actions do not forbid autonomy, but they change the
design: dry-run modes, approval gates (M13), and a much smaller blast radius.

**5. Can you evaluate it?** If you cannot tell automatically whether a run succeeded, you cannot tune
it, cannot catch regressions, and will not know it broke until a user tells you.

::: warn Question 5 is a veto
The other four are trade-offs. This one is not. If the honest answer is no, the work in front of you
is building the eval set (M8) — not building the agent. An agent you cannot measure is not a
prototype, it is a liability with a demo.
:::

::: autopsy “Agentic” as a synonym for “good”
Three post-mortems, same shape. A document-classification pipeline rebuilt as an agent: 6× the cost,
4× the latency, and *worse* accuracy, because the fixed pipeline's per-stage prompts were tuned and
the agent's general prompt was not. An internal search tool given a full agent loop when a single
retrieval call answered 90% of queries — the loop's extra turns mostly re-searched. And a data-entry
automation where the agent's flexibility became the bug: it "helpfully" corrected values the
customer had deliberately entered. In all three, no one had asked question 1.
:::
