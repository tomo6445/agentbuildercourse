## The patterns are the same

You now have the whole vocabulary: workflows and agents (M4), tool design (M2), context (M3), memory
(M7), testing (M8), several agents (M9), visibility (M10), security (M11), cost (M12).

Eight domains follow. The striking thing is how little the architecture actually varies between
them — you will recognise every arrangement.

What varies enormously is **what goes wrong**. Each domain punishes a different mistake, and it is
usually not the one your instincts are guarding against. That is what this module is for: knowing
the patterns tells you how to build it, and only knowing the domain tells you what to fear.

::: key
The patterns are the same. The failure modes are not.
:::

::: jargon Blast radius
How far the damage spreads when something goes wrong: does it affect only this run, only this user,
every customer, or all of production?

Along with reversibility (M13), it is the main thing that decides how much freedom an action gets.
:::

Read all eight even though you will only build two. The value is not the architectures — you already
know those. It is the catalogue of what goes wrong, which is the thing you cannot derive from first
principles and cannot afford to learn one incident at a time.

## Software engineering

**Architecture:** autonomous agent · file and shell tools · checkpointing · test-gated loop.

The canonical agentic domain: the path genuinely cannot be enumerated, feedback is immediate and
machine-readable, and errors are cheap in a branch.

**What bites you: verification.** "It compiles" is not "it works", and an agent optimising for a
green build will produce a green build. Without a test gate you get plausible code that passes review
and fails in production.

**Do:** make the tests the thing the loop is trying to satisfy, not a step within it. Work in an
isolated copy of the code. Save after every turn — long tasks and crashes are routine here. And never
let the agent change the tests it is being judged by, which it will do, entirely sincerely, given the
chance.

## Research and analysis

**Architecture:** orchestrator-workers · wide parallel search · synthesis with citations.

The domain where multi-agent genuinely pays (M9): parallelisable, read-heavy, and valuable enough to
absorb the multiple.

**What bites you: source quality.** Agents drift toward SEO content farms, because they are optimised
to be extractable — clean structure, quotable sentences, confident phrasing. The output looks
excellent and is sourced from nothing.

**Do:** put source quality in the rubric explicitly (M8). Give explicit heuristics — prefer primary
sources, prefer the filing over the article about the filing. Require a citation per claim and assert
it in evals. Surface conflicts rather than averaging them.

## Data and business intelligence

**Architecture:** routing plus SQL tools · read-only credentials · validation before execution.

**What bites you: schema hallucination and silent wrong answers.** A query against a misremembered
column name errors, which is fine. A query with subtly wrong join semantics returns a plausible
number, which is not. Nobody checks a number that looks reasonable.

**Do:** read-only credentials, always — the agent should be unable to change anything even if
persuaded to try. Give it the database structure as reference material (M6) rather than hoping it
remembers. Check queries before running them. Add sanity checks: does the row count look plausible,
does the total fall in a range you expect. And **show the query next to the answer, every time** — a
number without its query is a number nobody can check.

```python title=domains/bi/sanity.py
def run_query(sql: str, expectations: dict) -> dict:
    """Execute a read-only query and refuse to return a silently wrong answer."""
    reject_if_not_select(sql)          # properly parsed, not pattern-matched
    rows = readonly_conn.execute(sql).fetchall()

    warnings = []
    if expectations.get("min_rows") and len(rows) < expectations["min_rows"]:
        warnings.append(
            f"returned {len(rows)} rows, expected at least "
            f"{expectations['min_rows']} — check the join"
        )
    if (total := expectations.get("total_within")) and rows:
        actual = sum(r[expectations["total_column"]] for r in rows)
        if not (total["low"] <= actual <= total["high"]):
            warnings.append(
                f"total {actual:,.0f} is outside the expected range "
                f"{total['low']:,.0f}-{total['high']:,.0f}"
            )

    # The query goes back with the answer, always. A number without its query
    # is a number nobody can check.
    return {"sql": sql, "rows": rows, "warnings": warnings}
```

## Customer operations

**Architecture:** routing workflow with an escalation ladder · policy retrieval · tight scope.

Rarely a full agent. Routing plus specialised handlers is faster, cheaper and far more predictable at
volume.

**What bites you: confident wrongness at scale.** One wrong answer is a ticket; the same wrong answer
delivered five thousand times before anyone notices is a regulatory problem.

**Do:** scope tightly and escalate aggressively — the correct action is often "hand to a human".
Require a citation to a specific policy document for anything consequential. Monitor for distribution
shift in the answers themselves, not just in volume. Make abstention a rewarded outcome in your evals
(M8), or you will optimise it away.

## Document processing

**Architecture:** prompt chaining plus evaluator-optimiser · per-field confidence · human review
queue.

**What bites you: the awkward minority, and silent shortening.** 95% of documents match the format
you tested. The remaining 5% has no limit — scans, sideways pages, tables split across pages,
handwriting — and the failure is a confidently extracted wrong value rather than an error.

**Do:** per-field confidence, and route low-confidence fields to human review rather than guessing.
Never truncate silently (M2). Sample the tail deliberately when building the eval set; the tail is
where your accuracy actually lives.

## DevOps and SRE

**Architecture:** narrow, high-privilege tools · dry-run first · approval on mutations · exhaustive
audit.

**What bites you: how far the damage reaches.** These agents hold the most dangerous tools of any
domain, and M11's three-capability combination is present here **by default**, not by mistake:
private data (infrastructure state, secrets), untrusted content (logs, alerts, tickets, third-party
status pages), and a way to act on the world (changing production).

Worth sitting with: log lines are written by whoever can reach your systems, which means an attacker
can put text in front of your operations agent on purpose.

**Do:** dry-run everything by default; `apply` is a separate, gated mode. Approval on every mutation
(M13) — this is the domain where rung 2 is correct. Audit everything durably. Narrow the tools:
`restart_service(name)` not `bash`. And write the threat model down, because this is the domain where
someone will eventually inject a log line on purpose.

## Sales and CRM

**Architecture:** MCP-heavy integration · memory for account context · write validation.

**What bites you: data hygiene and PII.** An agent with write access to a CRM can degrade it faster
than a team can repair it — duplicates, malformed fields, overwritten human notes. Meanwhile customer
records are exactly the private data leg of the trifecta.

**Do:** validate every write against the schema and against existing records. Deduplicate before
creating. Never overwrite a human-authored field — append. Run a redaction hook on every result
(M5), because CRM data will otherwise end up in your traces, logs and evals.

## Personal and internal automation

**Architecture:** scheduled agents · narrow scope · self-reporting.

The domain that looks easiest and has the worst failure mode.

**What bites you: unattended failure nobody notices.** A nightly agent breaks in week one and
"succeeds" silently for three weeks. Nobody is watching, because the entire point was not to have to
watch.

**Do:** alerting and self-reporting *are* the design, not additions to it. Report every run,
including successful ones, so silence is itself an alarm. Assert on outputs, not just exit codes.
Set a dead-man's switch: no run in 26 hours pages someone. And put a hard budget cap on it, because
an unattended agent in a retry loop is unattended for a long time.

```python title=domains/scheduled/run.py
def nightly():
    """Report every outcome. Silence must be the only thing that is impossible."""
    started = time.time()
    try:
        result = agent.run(TASK, budget=Budget(max_usd=2.00))
        # Exit code 0 is not success. Assert on the artifact.
        assert result.rows_written > 0, "produced no rows"
        assert result.freshness_hours < 24, "source data was stale"
        report("ok", rows=result.rows_written, usd=result.usd,
               seconds=time.time() - started)
    except BudgetExceeded as exc:
        report("budget", detail=str(exc))          # distinct from a crash
        raise
    except Exception as exc:
        report("failed", detail=repr(exc))
        raise
    finally:
        heartbeat.touch()      # a dead-man's switch pages if this stops happening
```

::: deeper Where to run it
Two broad shapes, and the choice is usually forced by constraints rather than chosen on preference.

| | You run it | Anthropic runs it |
| --- | --- | --- |
| You operate | Everything | Just the client |
| Control | Total | Whatever the configuration exposes |
| Where data goes | Wherever you put it | Governed by the provider's terms |
| Long tasks | You build resuming and scheduling | Sessions and schedules included |
| Sandbox (M11) | You build and harden it | Provided per session |
| Best when | Strict rules about where data may live, unusual runtime, existing infrastructure | You want the loop and the sandbox operated for you |

Rules about where data may live usually decide it. Speed rarely does. "We need full control" is
often overstated — right up until the first time you need to change something the configuration does
not let you reach.
:::

::: autopsy Same architecture, four domains, four different deaths
The same orchestrator-workers system, adapted four times.

In **research**, it died on source quality — beautifully synthesised, sourced from content farms. In
**BI**, it died on a join: a plausible number, wrong, acted on for a month. In **document
processing**, it died on the 5% tail — the eval set was built from the documents that were easy to
collect, which were the ones that parsed. In **DevOps**, it died on blast radius: a dry-run flag that
defaulted to false.

Four teams, four architectures they could each defend, four failures none of them was watching for.
Pattern literacy told them how to build it. Only domain literacy told them what to fear — and that
comes from the failure catalogue of the domain, not from the architecture diagram.
:::
