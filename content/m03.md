## The problem nobody warns you about

You build an agent. It works beautifully. You give it a longer task, and somewhere around turn
twenty-five it starts getting worse — forgetting things you told it, ignoring earlier instructions,
giving vaguer answers.

Nothing errors. Nothing in the logs looks wrong. The obvious conclusion is that the model got worse,
or something is broken.

Neither. You ran out of **attention**.

::: key
Every token you add is a token of attention you spend. Context is a budget, not a bucket.
:::

Remember the context window from F1 — the model's desk, not its memory. Everything you send has to
fit on that desk, and everything on the desk competes for the model's attention.

The window is large. It is not free. As it fills, the model's ability to reliably use any particular
piece of it degrades.

::: warn It is a slope, not a wall
If you exceeded the window, you would get an error and you would know.

This is worse: performance falls off **gradually**. Recall gets patchier, early instructions lose
their grip, the model leans on whatever is nearest the end. No error, no warning, no log line — your
answers just get worse, and someone blames the model version.
:::

## What is actually in there

For a running agent, the window is usually filled roughly like this:

| What | Typical share | Can you shrink it? |
| --- | --- | --- |
| Your instructions | 1–5% | Rarely — small and load-bearing |
| Tool descriptions | 5–30% | Yes — consolidate (M2) |
| The conversation | 5–15% | Somewhat |
| **What tools returned** | **50–85%** | **Yes — this is where the work is** |

**Tool results dominate**, and almost nobody guesses that. A file you read, a search result, a
database query — each lands whole in the conversation and, because of how conversations work (F4),
gets **re-sent on every later turn**. Turn 20 is still paying for the search result from turn 3.

That single fact decides your strategy. Polishing your instructions while tool results are 70% of
the window is rearranging the furniture.

## Writing instructions at the right height

Your instructions to the model — the **system prompt** — can fail in two opposite directions.

::: jargon System prompt
Instructions sent with every request that set up who the model is and how it should behave. Separate
from the conversation, and passed as `system="..."` in the API call.
:::

**Too specific** is a pile of rules for every situation you have met. Brittle: the moment reality
supplies a case you did not list, there is nothing to fall back on. It also grows forever, because
every incident adds a rule.

**Too vague** is "be helpful, use good judgement". Nothing to act on, and no way for the model to
know what *your* organisation considers correct.

What you want is a clear frame plus the specifics that are genuinely non-obvious:

```text
You are a support triage agent for an enterprise software product.

Your job: correctly categorise and route each ticket, and answer directly when
the answer is unambiguous and documented.

Route to a human when: the customer mentions legal action, cancelling, or a
security problem; the account is Enterprise tier and unresolved after one
exchange; or you are not confident in the policy you are citing.

Always cite the policy document you relied on. If no document covers the case,
say so and route to a human rather than working it out from first principles.

Never quote pricing from memory — use the billing_get_plan tool.
```

Every line there is something the model could not have worked out. None of it is a flowchart.

That last line is F1 applied: the model will happily produce a plausible price from training. Making
it look the price up is exactly the fix.

### Examples beat rules

Three or four *varied* examples usually work better than a page of rules, and cost fewer tokens. An
example carries tone, format and judgement all at once.

The word doing the work is *varied*. Four examples of the same easy case teach nothing. Pick the
ordinary case, the ambiguous one, the one that must be escalated, and the one that looks in-scope
but is not.

## Fetch on demand instead of pre-loading

The instinct is to gather everything possibly relevant and send it all. For agents there is a better
default.

**Send a list of what exists, plus a tool to fetch any of it.** Titles, identifiers, a one-line
summary each. The model reads the list, decides which two matter, and asks for those.

This works because the model can see the *shape* of what is available without paying for the
contents — and because a filename is itself information. `2026-q3-revenue-final.xlsx` tells you
something before you open it.

The result: the context ends up holding what was actually needed, rather than what you guessed might
be.

Pre-loading still wins when there are only a handful of documents and all of them are relevant.
Decide on purpose rather than by habit.

## Three ways to handle long tasks

Eventually a conversation outgrows the window, or outgrows the point where the model handles it well.
There are three answers, and mature agents use all three.

### 1. Summarise the old part

When the conversation gets long, replace the early turns with a summary and carry on.

```python title=compaction.py
def compact(client, messages, keep_recent=10):
    """Replace everything older than the last N turns with a summary."""
    old = messages[:-keep_recent]
    recent = messages[-keep_recent:]

    if not old:
        return messages

    summary = client.messages.create(
        model="claude-opus-5",
        max_tokens=2000,
        system=(
            "Summarise this agent transcript for its own future reference. "
            "Keep: the goal, decisions made and why, facts discovered with "
            "their sources, records already changed, and what is left to do. "
            "Drop: exploration that led nowhere, and raw tool output already "
            "acted on."
        ),
        messages=[{"role": "user", "content": render(old)}],
    )

    summary_text = summary.content[0].text
    return [{"role": "user", "content": "Earlier work:\n" + summary_text}] + recent
```

**The summarising instructions are the strategy.** A generic "summarise this" loses exactly what the
agent needs — which record it already updated, which approach it already ruled out — and it repeats
work with no memory of having done it.

### 2. Keep notes in a file

The agent writes findings to a file outside the conversation, and reads them back when needed.

```text
## Goal
Reconcile Q3 revenue between the ledger export and the board deck.

## Established
- Ledger total: 2,143,880  (source: ledger_q3.csv, turn 4)
- Deck total:   2,151,200  (source: board_q3.pdf p.12, turn 7)
- Difference: 7,320 — matches the unbilled-usage accrual (turn 11)

## Ruled out
- Currency differences: both figures are already in USD (turn 9)

## Next
- Confirm the accrual with the revenue team's memo
```

Cheap, readable by you during debugging, and it survives the program being killed — which makes it
the basis of memory in M7.

### 3. Give the sub-task its own window

Hand a chunk of work to a separate agent with its own context. It reads twenty documents, burns
80,000 tokens, and returns two paragraphs. Your main conversation grows by two paragraphs.

The most powerful option and the most expensive — you are paying for a whole extra context. That is
M9.

### Choosing

| | Summarise | Notes file | Separate window |
| --- | --- | --- | --- |
| Best for | Long single conversations | Work across several sessions | Exploring many things at once |
| Cost | One extra call per summary | Almost nothing | High — a full context each |
| Goes wrong when | The summary drops something | Notes grow stale or huge | Duplicate or conflicting work |
| Survives a crash | No | Yes | Partly |

The lab measures all three so you choose with numbers rather than instinct.

## Paying less for the same text

There is one more lever, and it is nearly free.

Every turn re-sends the whole conversation (F4). **Prompt caching** lets the provider keep the
unchanged front portion, so you are charged much less for re-sending it.

::: jargon Prompt caching
The provider stores the beginning of your request. If the next request starts with exactly the same
text, that part is reused and charged at roughly a tenth of the normal price.

It changes what you pay, not what is in the window. Attention is still spent.
:::

The rule that matters: caching works on the **beginning** of the request, and the request is
assembled in a fixed order — tools, then instructions, then conversation. **Any change anywhere in
that beginning throws away everything after it.**

So: **stable things first, changing things last.**

```python
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    tools=TOOLS,                       # fixed, always in the same order
    system=[{
        "type": "text",
        "text": SYSTEM_PROMPT,          # no timestamps, no per-request values
        "cache_control": {"type": "ephemeral"},
    }],
    messages=messages,                  # the changing part, after the marker
)

# Check it is working. Silence is not success.
print(response.usage.cache_read_input_tokens)
```

The mistakes that quietly double your bill, roughly in order of how often they happen:

- **A timestamp in your instructions.** `"Current time: 2026-08-20T14:22:31Z"` changes every request,
  so nothing ever caches. If the model needs the time, put it in the user's message instead.
- **Tools in a different order each run.** Sort them.
- **Editing your instructions mid-conversation.**
- **Switching model mid-conversation.** Different model, different cache.
- **Adding or removing a tool mid-conversation.** Tools come first, so this invalidates everything.

Notice the shape of all five: nothing fails, nothing warns, the bill just goes up. Watch
`cache_read_input_tokens`. If it stays at zero across repeated calls, something in your prefix is
moving.

::: autopsy "Just use the big context window"
Two runs of the same research task, both with plenty of room.

The first pre-loads forty documents, because it can. The second sends a list of forty titles and
fetches the four it needs.

The smaller one wins on accuracy — the model's attention is not spread across thirty-six irrelevant
documents — and it wins on speed and cost by a wide margin.

A large window is a safety margin, not a strategy. The question is never "does it fit". It is "does
every token in here earn its place".
:::

::: deeper Letting the API manage context for you
Two features do some of this work server-side.

**Context editing** (beta header `context-management-2025-06-27`) *removes* old tool results rather
than summarising them:

```python
context_management={"edits": [{"type": "clear_tool_uses_20250919"}]}
```

Given tool results are 50–85% of the window, clearing the stale ones is often the single
highest-value change available.

**Compaction** (beta header `compact-2026-01-12`) summarises earlier context automatically as you
approach a threshold. One catch that costs people hours: append the whole `response.content` back
into your messages, not just the text. The compaction blocks are how the API knows what it already
summarised, and pulling out only the text silently loses that.
:::

## What you now know

- Context is **attention**, and it degrades **gradually** with no error.
- **Tool results** are most of what fills the window, and they are re-sent every turn.
- Instructions should be **specific but not a flowchart**; varied examples beat rule lists.
- **Fetch on demand** rather than pre-loading — send identifiers, load what is needed.
- Three long-task strategies: **summarise**, **notes**, **separate windows**. Choose with numbers.
- **Prompt caching** cuts what you pay to re-send; anything changing near the front breaks it
  silently.
