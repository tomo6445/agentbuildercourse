::: objectives
- Write a tool description that tells the model when to use it, not just what it is
- Understand that the description is read by the model, so it is part of your instructions
- Say why every tool costs you money on every single turn
- Make wrong answers structurally impossible rather than merely discouraged
- Write errors and results the model can actually recover from
- Fix a failing agent by changing only the tool descriptions
:::

## The thing beginners always blame is rarely the problem

You build an agent. It picks the wrong tool. It passes nonsense arguments. It tells the user a
customer does not exist when they plainly do.

The natural conclusion is that the model is not good enough. It is almost never that.

::: key
Tool descriptions are instructions to the model. Most "the model is bad at this" problems are "the
description was unclear" problems.
:::

Remember from M1: you give the model a list of tools, described in words. That description is
**everything the model knows** about your tools. It cannot read your code. It cannot ask a
colleague. It cannot try one and see. It reads your sentences and decides.

If two of your descriptions sound alike, it will confuse them — and so would a person.

## What a tool definition actually is

Three parts. In F3 you learned that a dictionary holds labelled information; this is one.

```python title=weather_tool.py
weather_tool = {
    "name": "get_weather",

    "description": (
        "Get current weather conditions for a city. "
        "Use this whenever the user asks about weather, temperature or "
        "conditions right now. "
        "Returns the temperature in Celsius and a one-word sky description. "
        "Returns a clear 'unknown city' message, not an error, if the city "
        "is not recognised."
    ),

    "input_schema": {
        "type": "object",
        "properties": {
            "city": {
                "type": "string",
                "description": "City name, for example 'Oslo'.",
            },
        },
        "required": ["city"],
    },
}
```

**`name`** — what the model writes in a `tool_use` block.

**`description`** — the part that does the work. Keep reading.

**`input_schema`** — what information the tool needs.

::: jargon Schema
A description of the shape information should have: which pieces there are, what type each one is,
and which are required.

Reading the one above: it is an object (a dictionary) with one property called `city`, which is a
string (text), and it is required. `properties` and `required` are just labels in a dictionary —
you already know the shape.
:::

## The description is a prompt

Read that description again, pretending you are the model and it is all you have. It answers four
questions, in this order, and that order is worth copying:

1. **What does it do?** Get current weather for a city.
2. **When should I use it?** Whenever someone asks about weather right now.
3. **What comes back?** Celsius and a one-word sky description — so the model can plan.
4. **What does failure look like?** Unknown city is a message, not a breakdown.

Most descriptions in the wild answer only the first, in about six words. `"description": "Gets
weather."` Then people are surprised when the model uses it for a forecast.

Question 4 matters more than it looks. Without it, a search that returns nothing gets reported to
the user as *"that customer does not exist"* — when the truth was "that query was too narrow, try
again". The model has no way to know which unless you say so.

## Every tool costs money on every turn

This surprises people, so let us be concrete.

Tool descriptions are sent to the model **on every single turn**, whether or not any tool is used.
They are part of what you pay for as input tokens (F4).

Forty tools, averaging 300 tokens of description each, is about **12,000 tokens per turn** — before
the user has said anything. On a fifteen-turn task, that is 180,000 tokens of pure description.

Three things follow:

- **Every tool has to earn its place.** "It might be useful someday" is a bill you pay per turn,
  forever.
- **Length is a real trade-off.** Longer descriptions genuinely improve accuracy, up to a point.
  Pay for sentences that change behaviour; cut ones that restate the name.
- **Fewer, better tools beat many vague ones**, for cost and accuracy at the same time.

## Name tools after jobs, not database tables

The instinct, if you have seen an API before, is one tool per operation: `list_events`,
`get_event`, `create_event`, `update_event`, `delete_event`, `check_availability`, `add_attendee`.

Now the model has to chain five of them to book a meeting. Five round trips, five chances to go
wrong, five lots of latency and tokens.

Replace them with one tool shaped like the actual task:

```python
schedule_event = {
    "name": "calendar_schedule_event",
    "description": (
        "Schedule a meeting: finds a time when everyone is free, creates the "
        "event, and invites them — all in one step. "
        "Use this for any request to set up, book or arrange a meeting. "
        "Attendees can be names or email addresses; names are looked up "
        "automatically. "
        "Returns the time chosen, a link, and anyone who could not be invited. "
        "If no time works, returns the three closest alternatives rather than "
        "an error."
    ),
    ...
}
```

One call instead of five. And the fiddly part — working out overlapping free time, resolving names,
handling the no-slot case — now lives in **your** code, where you can test it, instead of being
improvised by the model across five separate turns.

**Name tools after what someone wants to accomplish.** If a tool name is a verb from your database,
look again.

::: jargon Namespacing
Putting a prefix on tool names to say which system they belong to: `crm_search_customers`,
`calendar_schedule_event`, `github_open_pr`.

Costs a few tokens. Buys you no name collisions when you add a second integration, and an obvious
grouping the model can reason about.
:::

## Making the wrong answer impossible

There is a manufacturing idea called *poka-yoke*: design parts so they cannot be assembled the wrong
way round. Apply it to your tools.

**A fixed set of options becomes an `enum`.** If `status` can only be `active`, `churned` or
`trial`, say so:

```python
"status": {
    "type": "string",
    "enum": ["active", "churned", "trial", "any"],
    "description": "Filter by account status. Use 'any' unless asked to narrow it.",
}
```

Without the enum, the model reasonably tries `"cancelled"` or `"inactive"`. Your search returns
nothing, and the model reports there are no such customers. Nothing errored; the answer is just
wrong.

With the enum, that whole category of failure stops existing.

**Say where identifiers come from.** A parameter called `customer_id` with no explanation gets
invented. Write *"the customer_id returned by crm_search_customers"* and it gets looked up first.

**Replace true/false switches with named choices.** `force=true` is a coin flip. A `mode` parameter
with `["dry_run", "apply"]` says what it does, and the safe option is named.

**Describe every parameter.** An undescribed parameter is filled in by guesswork, and it is the most
common cause of malformed arguments there is.

## What comes back is also a prompt

Whatever your tool returns goes into the conversation and the model reasons from it. Shape it on
purpose.

**Turn identifiers into names.** `{"owner_id": "u_8823fa"}` forces another lookup or an invented
name. `{"owner": "Dana Ruiz", "owner_id": "u_8823fa"}` lets the model write the sentence
immediately.

**Return what is needed, not everything available.** Forty columns when three are wanted is
thirty-seven columns of distraction — and you pay for them again on every later turn.

**Say when there is more.** *"Showing 10 of 47 matches. Call again with page=2 for the next 10."*
Now the model knows both that more exist and exactly what to do.

**Never shorten something silently.** A tool that quietly cuts a long document down and returns it
unmarked produces confident, false answers with nothing anywhere looking like an error. If you
shorten, say so in what you return.

### Errors that help

| Unhelpful | Useful |
| --- | --- |
| `Error: invalid input` | `Error: 'status' must be one of active, churned, trial, any (got 'cancelled').` |
| `Error: not found` | `No customer matches 'j.smith'. Try a broader search, or search by account number.` |
| `Error: 500` | `The CRM is down for maintenance until 14:00 UTC. No lookup will succeed this session — tell the user and stop retrying.` |

That last one is the one people miss, and it is the fix for the retry loop from M1. A model has no
way to know a failure is permanent unless something says so. Without that sentence it will retry
until your turn limit stops it.

::: autopsy "The model is bad at this"
Six teams, same conclusion, same actual cause.

A tool described as `"gets records"` was picked almost at random against its three neighbours — they
all sounded the same. A date parameter with no format given produced nine different formats across a
hundred runs. A search that returned an empty list with no explanation had every empty result
reported to users as "that customer doesn't exist". A `limit` parameter with no maximum documented
got asked for 5,000 rows, which blew the context window.

In every case the model was doing exactly what the tool layer told it to. In the lab you rewrite the
descriptions, change nothing else, and watch the failures disappear.
:::

::: deeper Getting Claude to review your tool layer
A workflow that feels like cheating and is standard practice: give the failing runs to Claude and
ask which descriptions caused which failures.

You have the traces from M1, the tool definitions, and the list of what went wrong. Paste them in
and ask what to rewrite. It is unusually good at this, for an obvious reason — it is the reader you
are writing for, and it will flag ambiguities you cannot see because you know what you meant.

Do it *after* your own analysis rather than instead of it, and treat the output as a suggestion to
test. The eval set stays the judge (M8).
:::

::: deeper What happens past about thirty tools
Somewhere around thirty, adding another tool stops helping. Accuracy drops before you run out of
context: the model is choosing from a menu too long to hold clearly in mind, and near-duplicates
start attracting each other's calls.

Three fixes, in order of how much they change:

**Consolidate.** Most large tool sets are a few real jobs split across many operations.

**Split by agent.** Give each sub-agent only the tools its job needs (M9).

**Tool search.** Mark tools `defer_loading: true` and add a search tool
(`tool_search_tool_regex_20251119` or the BM25 variant), so definitions are fetched only when
relevant. Namespacing is a prerequisite — searching forty tools named `get`, `list` and `search`
retrieves the wrong ones faster. Never defer everything: the search tool and at least one other must
stay loaded, or the request is rejected.
:::

`labs/lab02_tool_surgery` gives you eight flawed CRM tools, twenty test tasks, and one rule: **only
the tool descriptions may change.** The agent, the prompt and the tests are frozen.

## What you now know

- A tool definition is a **name**, a **description**, and a **schema**.
- The description is read by the model, so it is part of your instructions. Say what it does, **when
  to use it**, what comes back, and what failure looks like.
- Descriptions cost tokens on **every turn**, used or not.
- Name tools after **jobs**, not database operations. One good tool beats five thin ones.
- **Enums, described parameters and named modes** make wrong answers impossible rather than
  discouraged.
- Results and errors are prompts too. Say what happened and what to do about it.
