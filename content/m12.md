## The surprising part

Cost per task has a few pieces: input tokens, output tokens, tool descriptions on every turn (M2),
built-in tool fees, and a multiplier if you use workers (M9).

The one that surprises people is **how input grows**.

Remember from F4 that every turn re-sends the whole conversation. So:

- Turn 1 sends 1 turn's worth.
- Turn 2 sends 2 turns' worth.
- Turn 10 sends 10 turns' worth.

Total across ten turns is 1+2+3+…+10 = 55. Across twenty turns it is 210.

**Doubling the turns roughly quadruples the input cost.** It grows with the square of the turn count,
not in a straight line.

::: warn What this means for optimising
It reorders everything. Halving your turn count beats halving your model price.

Most people's first instinct is to switch to a cheaper model. That helps. Reducing round trips —
better tools (M2), tighter results, fetching on demand (M3) — helps more, and costs no accuracy.
:::

::: widget cost-model
:::

Prices change, so keep them in one place rather than scattered through your code, and check the
current published rates before quoting any figure.

## Caching, properly

From M3: caching lets you pay much less to re-send an unchanged beginning. It is the highest-value
lever available and nearly free to adopt.

**Put stable things first, changing things last.** Requests are assembled in a fixed order — tools,
then instructions, then conversation — and any change anywhere in the beginning throws away
everything after it.

**Check it is working.** `usage.cache_read_input_tokens` is the only honest signal.

The changes that quietly double your bill, all of which pass code review:

| Change | Why it breaks |
| --- | --- |
| A timestamp in the instructions | The beginning differs on every request |
| Tools listed in a different order | Same content, different bytes |
| Editing instructions mid-conversation | The beginning changed |
| Switching model mid-conversation | Different model, different cache |
| Adding or removing a tool mid-run | Tools come first, so everything after is lost |

Every row is invisible in testing and expensive in production. Put cache hit rate on a dashboard
(M10) so a regression is a graph rather than a quarterly surprise.

## Sending easy work to cheaper models

Not every step needs your best model. Sorting, extracting and simple formatting run well on a small
one; planning and combining need a strong one.

```python title=routing.py
def choose_model(step):
    if step in ("classify", "extract", "format"):
        return "claude-haiku-4-5"          # cheapest
    if step in ("plan", "combine"):
        return "claude-opus-5"             # most capable
    return "claude-sonnet-5"               # in between
```

Two disciplines make this safe rather than merely cheap:

**Keep a quality floor.** Route cheap, then measure *each route* with your M8 tests. Any route
dropping below its floor goes back to the better model. Without this, routing is just a way to make
your product worse for money.

**Do not switch mid-conversation.** It invalidates the cache and can cost more than the model saved.
Use a separate worker (M9) for the cheap sub-task and keep the main conversation on one model.

Also consider batch processing for anything nobody is waiting on — overnight test runs, bulk
classification. Roughly half price.

## Why slow agents are slow

The thing people get wrong: **the slowest runs are slow because of the number of turns, not the speed
of each turn.**

Shaving 400ms off a turn is 400ms on a one-turn task and irrelevant against a task that sometimes
takes 25 turns. The slow tail is made of runs that took many more turns than usual. So:

- **Fewer turns.** Consolidating tools (M2) removes whole round trips.
- **Run independent tools at the same time.** The M1 lesson, and still the commonest avoidable delay.
- **Stream the output.** Does not make it faster; makes it *feel* much faster, which is what people
  report.
- **A turn limit set from data.** The run that takes 40 turns is usually thrashing, not working.

## Failing without making it worse

Normal web services taught us that a failed request is retried and forgotten. Agents are not like
that, and the same fault has very different consequences.

A crash at turn 18 of a 20-turn task loses eighteen turns of work **and** the money spent producing
them. Under load, that is an outage that is also a bill.

**Save after every turn** (M5). Resuming should be normal, not exotic.

**Make repeated actions safe.** If a resumed agent re-sends an email, something needs to recognise it
as the same email. Otherwise a resume becomes an incident.

### The retry storm

This is the one that catches everyone, and it looks reasonable at every step.

A rate limit is hit. Every running agent retries immediately. The retries arrive together, are also
rate-limited, and retry again. Now you have **more** load than the original traffic, sustained — and
every retry re-sends a full conversation, so the bill climbs while the success rate is zero.

Three things prevent it, and you need all three:

```python title=reliability.py
import random


def backoff_delay(attempt, base=1.0, cap=60.0):
    """Wait longer each time — and add randomness.

    The randomness is the part that matters. Without it, every client that
    failed together retries together, and you have rebuilt the original spike
    on a timer.
    """
    longest = min(cap, base * (2 ** attempt))
    return random.uniform(0, longest)
```

```python title=reliability.py
class CircuitBreaker:
    """Stop calling something that is down.

    Retrying a dependency that is completely down is load you are generating
    against yourself.
    """

    def __init__(self, failures_allowed=5, wait_seconds=30):
        self.failures_allowed = failures_allowed
        self.wait_seconds = wait_seconds
        self.failures = 0
        self.opened_at = None

    def allow(self, now):
        if self.opened_at is not None and now - self.opened_at > self.wait_seconds:
            self.opened_at = None          # try one and see
            self.failures = 0
        return self.opened_at is None

    def record(self, succeeded, now):
        if succeeded:
            self.failures = 0
            self.opened_at = None
        else:
            self.failures = self.failures + 1
            if self.failures >= self.failures_allowed:
                self.opened_at = now       # stop trying for a while
```

And the third: **a spending limit that stops the run** regardless of what the retry logic thinks it
is doing. Retries are how a small bug becomes expensive; the limit is what bounds the damage.

::: jargon Circuit breaker
Named after the electrical kind. After enough failures it "opens" and stops letting calls through
for a while, then lets one through to test whether the problem is over.

Without one, a dependency being down means every agent hammers it continuously — which often keeps
it down.
:::

## Deciding what "over budget" means

Decide **in advance** what happens when a limit is hit. There are three answers and they are product
decisions, not engineering ones:

- **Carry on with less** — a cheaper model, fewer workers, a partial answer clearly marked as partial.
- **Hand to a human**, with the work so far attached.
- **Stop and say so.**

Whichever you pick, write it down, and set limits per run, per customer **and** per task. A per-run
limit does not stop one customer consuming everything.

## Deploying while agents are running

The constraint that normal web services never taught you: **when you deploy, agents are mid-task.**

Stop a process and you kill a 20-turn task at turn 12. Multiply by your concurrent load. A rolling
deploy that is invisible for a web service is a mass-cancellation event for a fleet of agents.

The fix is to move traffic gradually and let old versions finish their in-flight work. New tasks go
to the new version; existing tasks finish where they started.

The catch worth knowing before you need it: both versions must understand the same saved-session
format. That is a compatibility constraint on a format you might otherwise change casually.

::: autopsy The retry storm
An occasional rate limit from a downstream service. The client retried three times with no
randomness. Two hundred concurrent agents hit the limit within the same second, all retried at one
second, all failed, all retried at two seconds.

Sustained load rose to about six times normal for eleven minutes. Every retry re-sent a full
conversation — averaging 40,000 tokens — so the bill for that window ran to four figures with a **0%
success rate**.

The dashboard showed nothing unusual until the invoice, because the agents were "working": no errors
surfaced to users, just slow tasks that eventually gave up.

Fixed with randomised backoff, a circuit breaker, and a spending limit that stops rather than retries
into a wall. The signal that would have caught it in minutes is cost per task — the first thing on
M10's watch list.
:::

::: deeper Durable execution for long-running agents
For agents that run for hours, saving to a file is not enough — you also want the work to survive the
machine going away.

A workflow engine records each completed step durably, so if the machine handling a task dies,
another picks it up from the last completed step rather than the beginning.

The trade is real complexity for the guarantee. It becomes worth it at exactly the point where tasks
become long and valuable — which is also the point where restarting from zero stops being tolerable.

Signs you have reached it: tasks routinely exceed an hour, a lost task means visible customer impact,
or you are already writing your own bookkeeping for which steps finished.
:::

## What you now know

- **Doubling the turns roughly quadruples the input cost.** Fewer turns beats a cheaper model.
- **Caching** is the highest-value lever; five ordinary-looking changes break it silently.
- **Route cheap work to cheap models**, with a quality floor per route, and never switch mid-run.
- Slow runs are slow because of **turn count**. Streaming fixes the feeling, not the number.
- A retry storm needs **randomised backoff, a circuit breaker, and a spending limit** — all three.
- Decide in advance whether hitting a limit degrades, escalates or stops.
- **Deploys kill in-flight agents** unless you let old versions finish.
