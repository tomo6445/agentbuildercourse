## Adopting someone else's loop

You wrote the loop in M1. Now the honest question: should you keep it?

Usually not. Other people have written this loop, handled the awkward cases, and given you sessions,
permissions and cost tracking for free. But adopting a framework without understanding it is how you
end up unable to debug anything — which is exactly why we did M1 first.

::: key
Here is the loop you should actually ship, and exactly which of your lines it replaces.
:::

## Four options

Two separate questions decide this, and mixing them up is why the choice confuses people:

**Who writes the loop?** and **whose computers does it run on?**

| | You write | Loop | Runs on | Tools included |
| --- | --- | --- | --- | --- |
| **Your own loop** | Everything | You | Your machine | Only yours |
| **Tool Runner** | Just the tool functions | The SDK | Your machine | Only yours |
| **Managed Agents** | Configuration | Anthropic | Anthropic | Sandbox + yours |
| **Claude Agent SDK** | A prompt and options | The SDK | Your machine | Files, shell, search + yours |

**Your own loop** is what you built. Keep it when you need control the others do not offer.

**Tool Runner** is part of the ordinary Anthropic library. It runs the loop over tools *you* write:

```python title=tool_runner.py
from anthropic import Anthropic, beta_tool

client = Anthropic()

@beta_tool
def get_weather(city: str) -> str:
    """Get current conditions for a city.

    Use this when someone asks about weather right now.

    Args:
        city: City name, for example 'Oslo'.
    """
    return "4C, light rain"

runner = client.beta.messages.tool_runner(
    model="claude-opus-5",
    max_tokens=16000,
    tools=[get_weather],
    messages=[{"role": "user", "content": "Weather in Oslo?"}],
)

for message in runner:
    ...        # one turn each time around; it stops when Claude is done
```

That replaces your **entire** M1 `run()` function. The tool description is generated from the
docstring — which means everything in M2 now applies to your docstrings.

::: jargon Decorator
The `@beta_tool` line above a function. It is a marker that hands your function to something else to
modify or register.

Read `@beta_tool` as "treat this function as a tool". You do not need to know how they work to use
them.
:::

**Managed Agents** is the only option where Anthropic runs both the loop and the computer the tools
execute on. Good when you want long-running, resumable, scheduled agents without operating any of it.

**Claude Agent SDK** is a different product — Claude Code as a library. It comes with tools for
reading and writing files, running shell commands and searching, plus permissions and sessions.

::: warn Tool Runner is not the Agent SDK
They sound alike and are unrelated packages.

**Tool Runner** is a small helper in the normal API library. It loops over tools *you* write and
ships none of its own.

**Claude Agent SDK** is a separate package with built-in file and shell tools.

Both run on your machine. Only Managed Agents runs on Anthropic's. Getting this wrong sends people
hunting for filesystem tools in the wrong library for an afternoon.
:::

## What you stop maintaining

The honest way to adopt a framework is to know which of your lines it is deleting.

| Your M1 code | What you get instead |
| --- | --- |
| The `while` loop over `stop_reason` | The loop, including `pause_turn` |
| Looking up tools by name | Registration and dispatch |
| Building error results by hand | Errors returned to the model automatically |
| `messages.append(...)` bookkeeping | Saved conversations that resume |
| Your turn and budget counters | Cost tracking, and places to enforce a ceiling |
| Your list of turn records | Structured events (M10) |
| Ad-hoc "should I allow this?" checks | A rules layer you declare |
| Nothing | Built-in file, shell and search tools |

Everything in the left column still exists. You are now debugging someone else's version of it —
which is fine, because you know what it is supposed to be doing.

## Sessions: not starting over

Your M1 agent kept the conversation in a variable. Close the program and it is gone.

A **session** saves it, so a crash at turn 30 is a resume rather than a lost hour.

::: jargon Session
A saved conversation, stored somewhere that survives the program stopping — a file or a database.

Save after every turn. The moment you want it is exactly the moment you cannot create it.
:::

```python title=session.py
import json
from pathlib import Path


def save(session_id, messages, turn, spent):
    """Write the conversation to a file after every turn."""
    path = Path("sessions") / (session_id + ".json")
    path.parent.mkdir(parents=True, exist_ok=True)

    # Write to a temporary name first, then rename. A crash halfway through
    # a write would otherwise leave a corrupt file — and you would discover
    # that at the exact moment you needed it.
    temporary = path.with_suffix(".tmp")
    temporary.write_text(json.dumps({
        "messages": messages, "turn": turn, "spent": spent,
    }))
    temporary.replace(path)


def load(session_id):
    """Read it back, or return a fresh start if there is nothing saved."""
    path = Path("sessions") / (session_id + ".json")
    if not path.exists():
        return {"messages": [], "turn": 0, "spent": 0.0}
    return json.loads(path.read_text())
```

### Branching, which is the real trick

The underused capability is **forking**: take a saved conversation, branch it at turn 14, change one
thing, and run both.

That is a controlled experiment, and it is the only reliable way to answer questions like:

- Did the new tool description fix it, or did the run just come out differently?
- Was it the summarising step, or the tool result just before it?

Without it, you re-run whole tasks and compare outcomes that vary anyway, which needs many runs to
say anything. With it, you change one thing. M10 builds its whole debugging approach on this.

## Permission rules

A permissions layer decides, per tool call, whether to allow it, refuse it, or ask a human.

```text
allow:  read_file, grep, web_search
ask:    write_file, git_commit
deny:   send_email, http_post, bash containing "curl"
```

Genuinely useful. Now understand exactly what it is not.

::: warn A rule is a gate, not a wall
A rule matching `bash` commands containing `curl` is doing **text matching on input an attacker may
control**. The same action can be written `/usr/bin/curl`, `$(which curl)`, a variable, a
base64-encoded blob piped into a shell, or four lines of Python opening a network connection.

Every deny-list is a claim that you thought of all the spellings. You did not.

Permission rules **are** worth having: they catch mistakes, which is most of what actually happens,
and they give a human a place to intervene. They stop a determined attacker only by luck. For that
you need a boundary the program cannot talk its way around — a machine with no network access, a
filesystem that does not contain the secrets. That is M11.
:::

The lab makes you prove this on your own rules, which is more convincing than being told.

## Hooks: your code at fixed points

A **hook** runs code you wrote at a defined moment — before a tool runs, after it returns, when a
session starts.

::: jargon Hook
A place where the framework stops and runs your function, letting you inspect or change what is
happening.

"Before every tool call, run this." "After every result, run that."
:::

Four things they are genuinely good for:

**Checking before running.** Refuse a write outside the working folder; refuse an email to an
outside address when policy says internal only.

**Removing sensitive information** from results before they enter the conversation — which also
keeps it out of your logs and your saved traces, where it otherwise leaks from.

**Recording everything.** Every tool call, its arguments, and what happened. Do this from day one.
It costs nothing and is the difference between explaining an incident and shrugging.

**Stopping on cost.**

```python title=cost_ceiling.py
class BudgetExceeded(Exception):
    """Raised to stop the run before the bill does it for us."""


class CostCeiling:
    def __init__(self, limit_dollars):
        self.limit = limit_dollars
        self.spent = 0.0

    def after_turn(self, usage):
        self.spent = self.spent + (usage.input_tokens * 5.00
                                   + usage.output_tokens * 25.00) / 1_000_000
        if self.spent >= self.limit:
            raise BudgetExceeded(
                "spent $" + str(round(self.spent, 4)) +
                ", which hits the $" + str(self.limit) + " ceiling"
            )
```

Decide **in advance** what hitting a ceiling does — degrade, escalate to a human, or stop. Working
that out at 3am is worse.

::: autopsy Hooks are policy, not protection
A team put personal-data removal in a hook and called the system compliant. The hook cleaned results
from the tools it knew about.

Then somebody connected another integration. Its tools did not match the hook's patterns, and
unredacted customer records began leaving the building through a path the compliance review had
already approved.

A hook that asks nicely is a policy. Policies belong in hooks. Actual protection belongs in the
network and the filesystem, where nothing can route around it.
:::

::: deeper Structured output, when something downstream reads the answer
When another program consumes your agent's answer, you need a fixed shape rather than prose. Ask for
a schema:

```python
response = client.messages.parse(
    model="claude-opus-5",
    max_tokens=16000,
    messages=[{"role": "user", "content": brief}],
    output_config={"format": {
        "type": "json_schema",
        "schema": {
            "type": "object",
            "properties": {
                "category": {"type": "string",
                             "enum": ["billing", "technical", "account"]},
                "confidence": {"type": "number"},
                "citations": {"type": "array", "items": {"type": "string"}},
            },
            "required": ["category", "confidence", "citations"],
            "additionalProperties": False,
        },
    }},
)
```

`messages.parse()` validates it for you. Two things that will otherwise cost you an afternoon: the
old trick of starting the model's reply with `{` to force JSON now returns an error on current
models — structured output replaces it — and this feature cannot be combined with document
citations, so put citations in your schema as fields instead.
:::

## What you now know

- Four options: **your own loop, Tool Runner, Managed Agents, Claude Agent SDK.** Two questions
  separate them: who writes the loop, and whose computer it runs on.
- **Tool Runner ≠ Agent SDK.** Different packages, different scope.
- A **session** is a saved conversation. Save every turn; a crash becomes a resume.
- **Forking** a session lets you change one thing and compare — a real experiment.
- **Permission rules** catch mistakes. They are not protection against someone trying.
- **Hooks** run your code at fixed points: checking, redacting, logging, stopping on cost.
