## An agent is a while-loop

Strip away the vocabulary and an agent is this:

```python
while True:
    response = call_the_model(messages)
    if response.stop_reason != "tool_use":
        break
    messages.append(assistant_turn(response))
    messages.append(results_of_running(response.tool_calls))
```

That is the whole idea. A model that can ask for actions, a loop that performs them, and a
transcript that carries the consequences forward. Everything else in this course — harnesses,
protocols, evaluation, sandboxes, cost models — is engineering built around those six lines.

The reason we start here, by hand, is not nostalgia. It is that **every bug you will hit for the
next fifteen modules is a bug in this loop or in what you fed it.** A student who understands the
loop can debug any framework. A student who only knows a framework can debug nothing, because when
the framework misbehaves they have no model of what it was supposed to be doing.

::: key
An agent is a while-loop with a language model in it. Everything else is ergonomics.
:::

## The single turn: what actually crosses the wire

Before the loop, the turn. One request, one response.

```python title=one_turn.py
import anthropic

client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY, or an `ant auth login` profile

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,
    system="You are a precise assistant. Prefer tools over recollection.",
    messages=[{"role": "user", "content": "What's the weather in Oslo?"}],
    tools=[{
        "name": "get_weather",
        "description": (
            "Get current weather conditions for a city. Use this whenever the user asks "
            "about weather, temperature or conditions right now. Returns temperature in "
            "Celsius and a one-word sky description. Returns an error for unknown cities."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "City name, e.g. 'Oslo'."}
            },
            "required": ["city"],
        },
    }],
)

print(response.stop_reason)   # -> 'tool_use'
for block in response.content:
    print(block.type)         # -> 'text', then 'tool_use'
```

Three things in that response deserve your full attention.

**`response.content` is a list of blocks, not a string.** A turn can contain a text block, several
`tool_use` blocks, and thinking blocks, in any combination. Code that does `response.content[0].text`
works on your first demo and breaks on your second.

**`stop_reason` is the control signal.** It is how the model tells your loop what to do next:

| stop_reason | Meaning | What your loop does |
| --- | --- | --- |
| `end_turn` | The model finished its answer | Exit the loop; return the text |
| `tool_use` | The model is requesting one or more tool calls | Execute them, append results, continue |
| `max_tokens` | Output hit your `max_tokens` ceiling | Raise or continue; never treat as success |
| `stop_sequence` | A stop sequence you configured was emitted | Application-specific |
| `pause_turn` | A long-running server-side tool paused the turn | Re-send the turn to resume it |
| `refusal` | A safety classifier declined the request | Check `stop_details`; do not read `content` as an answer |

The single most common structural bug in a hand-rolled loop is branching on the *presence of
tool_use blocks* rather than on `stop_reason`, and then silently mishandling `max_tokens` and
`pause_turn`. Branch on `stop_reason`. Then look at the blocks.

**A `tool_use` block is a request, not an action.** This is the distinction that half of all agent
confusion lives inside.

## The model does not call your function

Say it out loud, because the vocabulary is actively misleading. "Function calling" and "tool calling"
both suggest that the model reaches out and invokes something. It does not. It cannot. It has no
network, no process, no filesystem.

What actually happens is that the model emits a block of structured text:

```json
{
  "type": "tool_use",
  "id": "toolu_01A9FqvKbT7X",
  "name": "get_weather",
  "input": {"city": "Oslo"}
}
```

That is model output. It is generated the same way the word "Oslo" is generated. It has exactly the
same epistemic status as any other thing a model says, which means:

- It can name a tool that does not exist.
- It can supply arguments that violate your schema.
- It can request an action the user never authorised.

**Your code is what turns that text into an effect.** Your code is therefore where validation lives,
where the permission check lives, where the audit log lives, and where the blame lives. A prompt that
says "never delete files" is a preference. A dispatcher that refuses to route `delete_file` is a
control.

::: warn Where the security boundary really is
This is why M11 exists, and why it is not optional. Every gate you can only express in the prompt is
advisory. Every gate you express in the dispatcher is enforced. When you catch yourself writing
"the model shouldn't do X" in a system prompt, ask what happens when it does.
:::

## The full round trip

Now assemble it. The loop below is close to what you will write in Lab 1 — it is deliberately plain,
and every line earns its place.

```python title=tinyagent.py
import json

MAX_TURNS = 10


def run(client, tools, registry, user_input, system=""):
    """Run an agent loop to completion. `registry` maps tool name -> callable."""
    messages = [{"role": "user", "content": user_input}]
    tool_defs = [t.definition for t in tools]

    for turn in range(MAX_TURNS):
        response = client.messages.create(
            model="claude-opus-5",
            max_tokens=16000,
            system=system,
            tools=tool_defs,
            messages=messages,
        )

        if response.stop_reason == "pause_turn":
            # A server-side tool paused mid-turn. Re-send to resume; do not
            # treat this as an answer.
            messages.append({"role": "assistant", "content": response.content})
            continue

        if response.stop_reason != "tool_use":
            return final_text(response), messages

        # 1. The assistant turn goes back verbatim, tool_use blocks included.
        messages.append({"role": "assistant", "content": response.content})

        # 2. Execute every requested call. All of them.
        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            results.append(execute(registry, block))

        # 3. Every result returns in ONE user message.
        messages.append({"role": "user", "content": results})

    return "Stopped: turn cap reached.", messages


def execute(registry, block):
    """Run one tool call. Errors become results, never exceptions."""
    fn = registry.get(block.name)
    if fn is None:
        return {
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": (
                f"Error: unknown tool '{block.name}'. "
                f"Available tools: {', '.join(sorted(registry))}."
            ),
            "is_error": True,
        }
    try:
        output = fn(**block.input)
    except Exception as exc:                      # noqa: BLE001 - deliberate
        return {
            "type": "tool_result",
            "tool_use_id": block.id,
            "content": f"Error: {type(exc).__name__}: {exc}",
            "is_error": True,
        }
    return {
        "type": "tool_result",
        "tool_use_id": block.id,
        "content": output if isinstance(output, str) else json.dumps(output),
    }
```

### Three rules the API will enforce, and one it will not

**Every `tool_use` needs a matching `tool_result`.** Same `tool_use_id`, in the very next user
message. Skip one and the request is rejected. This is a hard rule and you will hit it the first time
you write a `continue` in the wrong place.

**Send the assistant turn back verbatim.** Not a re-serialised approximation of it —
`response.content` as it came. Thinking blocks in particular must be echoed back unchanged when you
continue on the same model.

**Errors go back as results, not exceptions.** `is_error: True` with a message the model can act on.
A raised exception ends the run; a returned error lets the model try something else. This one line is
the difference between an agent that degrades gracefully and one that falls over.

**And the rule the API will not enforce:** return *all* parallel results in a *single* user message.
Splitting them across several messages is accepted by the API and quietly teaches the model to stop
making parallel calls, which shows up weeks later as unexplained latency.

## Parallel tool calls

One assistant turn can contain several `tool_use` blocks. When the model asks for the weather in two
cities, you get two blocks, and the correct response is to run both — concurrently, if they are
independent — and return both results together.

```python
import asyncio

async def execute_all(registry, blocks):
    """Independent calls run concurrently; the result order still matches."""
    tasks = [asyncio.to_thread(execute, registry, b) for b in blocks]
    return await asyncio.gather(*tasks)
```

Sequential execution of independent calls is the most common source of avoidable latency in agents.
It is invisible on a two-tool demo and painful at ten.

## Termination, and the three ways loops fail to stop

An agent that cannot stop is not an agent, it is an outage with a chat interface. There are three
distinct failure modes and they need three distinct defences.

**Error thrash.** A tool fails permanently; the model retries it; nothing in the context suggests
retrying is futile, so it retries again. Defence: a turn cap, always, plus errors that say what is
actually wrong ("the CRM is down for maintenance, no lookup will succeed this session" beats "500").

**Oscillation.** Two tools point at each other — one says results may be stale, the other says
re-search. The model bounces between them making no progress. Defence: hash `(tool_name, arguments)`
per turn and trip when the same pair repeats with no intervening state change. This is cheaper than
the turn cap and vastly more diagnosable, because you know *why* it stopped.

**Goal drift.** Nothing errors. The agent starts on Q3 revenue, finds an interesting competitor
mention on turn 2, and returns a competitive landscape memo. Defence: restate the goal in context
periodically, and compare the final output against the original instruction — this is an evaluation
problem (M8) as much as a loop problem.

On top of all three sits the budget cap. Turns are a proxy for cost; cost is the thing you actually
care about. Track tokens and dollars in the loop and abort on the real number.

```python
class Budget:
    """A cap the loop can actually enforce, rather than one you hope holds."""

    def __init__(self, max_turns=10, max_usd=0.50):
        self.max_turns, self.max_usd = max_turns, max_usd
        self.turns, self.usd = 0, 0.0

    def charge(self, usage, price_in, price_out):
        self.turns += 1
        self.usd += (usage.input_tokens * price_in
                     + usage.output_tokens * price_out) / 1e6

    @property
    def exhausted(self):
        return self.turns >= self.max_turns or self.usd >= self.max_usd
```

::: autopsy “The model called my function.”
It didn't. Trace any hallucinated tool name through your loop and watch what happens: a perfectly
ordinary, well-formed model output arrives naming a tool you never registered. The API returns 200.
Nothing is broken. Your dispatcher does a dictionary lookup and misses — and what it does next
decides whether your agent recovers or dies. Raise, and the run ends with a stack trace the user
never asked for. Return `is_error` with the list of tools that *do* exist, and the model reads it,
apologises, and picks a real one. Same model, same prompt, entirely different product.
:::

## Who runs it, who pays, what lands in your transcript

Not every tool is executed by you.

**Client-executed tools** — your custom tools, plus Anthropic-defined ones like bash, the text
editor and memory — are executed by your harness. You own the implementation, the security, the
latency and the failure modes. The tool definition costs context; the execution costs whatever your
infrastructure costs.

**Server-executed tools** — web search, web fetch, code execution — run on Anthropic's
infrastructure. You declare them and results arrive as content blocks in the same response, without a
round trip through your code. You give up the ability to intercept them, and you may see
`pause_turn` on long-running ones.

The practical consequences:

- Server tools do not pass through your dispatcher, so your permission checks and audit log do not
  see them. If that matters for a given action, it must be a client tool.
- Server tool results land in your transcript and are re-sent on every subsequent turn, so they are
  a context-budget problem (M3) as well as a capability.
- Server tools carry their own usage charges on top of tokens. Your cost model (M12) needs a term for
  them.

::: note Which loop should you actually ship?
Not this one. Once you understand the mechanics, the SDK's tool runner
(`client.beta.messages.tool_runner`) drives this loop for you, and the Claude Agent SDK — a separate
product — gives you the whole Claude Code harness. M5 makes that transition explicitly, mapping every
abstraction back to the lines above. Build it once by hand so that when the harness surprises you,
you know what it was supposed to be doing.
:::

## The Observatory

The second lab is the most important forty minutes in this course, and it looks like the least
important.

You are going to build a trace viewer. Not a logging library — a viewer. Something that takes the
structured record your loop emits and renders every turn as a card: role, content blocks, tool calls
and their arguments, token counts, latency, cumulative cost, stop reason.

It will be ugly. It does not matter. You will extend it in eleven of the remaining fifteen modules —
context occupancy in M3, cache hits in M3, eval run comparison in M8, subagent waterfalls in M10,
cost attribution in M12 — and by the end you will not be guessing why an agent misbehaved. You will
be reading it.

Design the trace record now, because changing it later is annoying:

```python title=trace.py
from dataclasses import dataclass, field, asdict
import json, time


@dataclass
class TurnRecord:
    index: int
    role: str                       # 'user' | 'assistant' | 'tool_result'
    blocks: list = field(default_factory=list)
    stop_reason: str | None = None
    input_tokens: int = 0
    output_tokens: int = 0
    cache_read_tokens: int = 0
    latency_ms: float = 0.0
    usd: float = 0.0


@dataclass
class Trace:
    task: str
    started_at: float = field(default_factory=time.time)
    turns: list = field(default_factory=list)
    outcome: str = "running"

    def add(self, record):
        self.turns.append(record)

    def to_json(self, path):
        with open(path, "w") as fh:
            json.dump(asdict(self), fh, indent=2)
```

Two fields there are worth more than they look. `cache_read_tokens` is how you find out that your
prompt cache silently stopped working — which is a bill problem you would otherwise discover monthly.
And `stop_reason` on every turn is how you spot a run that ended on `max_tokens` and was reported to
the user as a complete answer.
