::: objectives
- Decide how much freedom each kind of action gets, rather than rating the agent as a whole
- Design an approval request a person can actually make a decision from
- Recognise that asking too often destroys the control you built
- Let someone correct an agent mid-task without throwing the work away
- Show honest progress when nobody knows how many steps remain
- Give people a way to tell when to trust it
:::

## The question changes

By now you can build an agent that does the task. The remaining questions are harder, and they are
product questions rather than engineering ones.

**When should it ask?** And when it asks, **how does a person know whether to say yes?**

::: key
The hard question isn't "can the agent do it" but "when should it ask, and how does a human know
whether to say yes".
:::

## Six levels of freedom

1. **Suggest** — it proposes, a person does it.
2. **Ask every time** — it proposes each action and waits.
3. **Ask for the risky ones** — routine actions proceed; a defined set waits.
4. **Do it and say so** — it acts, the person is told afterwards.
5. **Do it, with undo** — it acts, and the person can reverse it.
6. **Just do it** — no notification, no undo.

::: warn Choose per action, not per agent
This is the mistake everyone makes first.

The same coding agent should read files at level 6 — asking permission to read teaches people to
click yes without looking — commit to a working branch at level 5, since version control makes undo
cheap and real, and wait for approval before overwriting the main branch at level 2.

Calling "this agent" semi-autonomous is a category error that manages to over-restrict and
under-restrict at the same time.
:::

Two things place an action: **can it be undone**, and **how far does the damage reach**. Cheaply
reversible and self-contained goes high. Irreversible or wide-reaching goes low.

## What a person needs in order to decide

Here is a real approval request. It is a machine for generating rubber stamps:

```text
Agent wants to run: bash
[Approve] [Deny]
```

Show that to somebody a hundred times a day and they learn exactly one behaviour, and it is not
careful review.

Four things make a decision possible:

**The action, concretely.** Not "bash" — `rm -rf ./build/cache` in `/srv/app`, affecting 340 files.

**Why.** What the agent believes this accomplishes.

**How far it reaches.** What changes, for whom, and whether it can be undone.

**What happens if you say no.**

That fourth one is almost always missing, and it is the one that turns a gate into a choice. Without
it, a person has no way to weigh anything — they can only guess at the cost of refusing.

```text
┌──────────────────────────────────────────────────────────────┐
│ Approve: delete 340 files                                    │
│                                                              │
│ ACTION      rm -rf ./build/cache   (in /srv/app)             │
│ WHY         Stale cache is hiding the dependency update      │
│ IMPACT      Generated files only. No source. Rebuilt in ~40s │
│ IF DENIED   Falls back to an incremental build, which may    │
│             reproduce the original error                     │
│                                                              │
│ [Approve]  [Approve all cache operations]  [Deny]  [Edit]    │
└──────────────────────────────────────────────────────────────┘
```

## Asking too often breaks the control

State it plainly, because it usually gets treated as a minor annoyance:

::: warn A person approving forty things a day is not reviewing anything
You have built a safety control whose reliability **degrades the more you use it** — and you have
done it in a way that looks responsible on a diagram and produces a clean audit trail.

Countermeasures:

**Tier by risk.** Only genuinely risky actions interrupt. If everything asks, nothing is read.

**Batch.** "The agent will change these 12 files: [list]. Approve all?" One considered decision beats
twelve reflexes.

**Learn from what has been approved.** "You have approved `npm test` 23 times. Always allow?"

**Scope the grants.** "Approve cache operations for this session" is bounded in time and kind, rather
than forever and everywhere.

**Measure it.** Track approvals per person per day, and how long decisions take. When the median
drops below about two seconds, your control has become a formality and you should know that.
:::

## Correcting it mid-task

Watching an agent go the wrong way with no way to intervene except killing it is a miserable
experience, and it throws away everything done so far.

**Pause** should stop cleanly at the next turn boundary, keeping the state.

**Steer** should let someone inject a correction the agent picks up and continues from — "no, use the
staging database" — without discarding twelve turns of context.

**Rewind** should let someone go back to turn 8 and take a different path. That is session forking
(M5) with an interface on it.

Design steering as an **operator** channel rather than an ordinary user message, so it carries more
weight than the untrusted user turn and does not get confused with it.

## Showing progress honestly

Agents break both assumptions a progress bar relies on: they do not know how many steps remain, and
the steps are not the same size.

What actually works:

**Show the work, not a percentage.** A live feed — "searching the ledger export", "reading
contract.pdf (page 4 of 12)" — is more informative and more honest than a made-up bar.

**Show the tool calls.** People trust an agent whose actions they can see, and they catch mistakes
earlier. This is legibility doing security work.

**Stream the output.** It does not go faster; it feels dramatically faster.

**Be honest about not knowing.** "Step 4 — about 3 more expected" beats a bar sitting at 80% for four
minutes. If you cannot estimate, say so.

**Show the cost as it accrues** when the person is paying. They need it to decide whether to
interrupt.

## Trusting it correctly

Both directions are product failures.

**Trusting too much** — output accepted without review, so errors flow straight through. Caused by
uniformly confident presentation and an early run of successes.

**Trusting too little** — everything verified anyway, so the agent saves nobody any time. Caused by
an early visible failure with no explanation, and by opaque behaviour.

The cure for both is the same: **let people see what it did**. An agent that shows its work, cites
its sources, says when it is unsure, and presents uncertainty differently from confidence lets a
person learn *when* to trust it rather than *whether* to.

Uniform confidence destroys that signal in both directions.

## Undo, dry runs and previews

Design these in from the start; they are painful to retrofit.

**Dry run.** Every action that changes something can report what it *would* do. This is also your
best debugging tool and your best demo.

**Preview.** Show the difference before applying it — the file changes, the records that will change,
the draft email.

**Undo.** A reversing action for every changing action, wherever possible. Where it is genuinely
impossible, that fact belongs **in the approval request**, because it is exactly what the person
needs to know.

::: warn Making an action reversible often beats gating it
A soft delete with a 30-day recovery window turns an irreversible action into a reversible one. It
moves from level 2 to level 5, removes an approval from someone's day, and is usually a few hours of
work.

Gating an irreversible action manages the problem. Making it reversible removes it.
:::

::: autopsy The approve-all button
A product shipped per-action approval. Users complained, so the team added "approve all for this
session".

Adoption was immediate and near-universal — clicked, on average, within the first ninety seconds.

The product was now fully autonomous, with an audit trail showing informed consent for every action.
The approval flow had not been removed; it had been made ceremonial. And the ceremony made the risk
*harder* to see, because the logs looked impeccable.

What worked instead: tier by risk so only genuinely risky things asked, batch the rest, and scope
grants by kind and session rather than leaving them unbounded. Approvals per session fell by about
80% — and the remaining ones started getting read. Median decision time went from 1.2 seconds to 9.
:::

::: deeper Designing the approval for the person, not the log
A useful test: hand your approval screen to somebody who did not build the agent and ask them to
decide. Do not explain it.

If they ask "what does that do?", the action is not concrete enough. If they ask "is that bad?", the
impact is missing. If they say "I suppose so", the alternative is missing — they are guessing at the
cost of refusing.

Three people, ten minutes, and you will fix more than a week of speculation would. The lab makes you
do exactly this with five classmates, and the graded part is what you changed afterwards.
:::

## What you now know

- Six levels, chosen **per action**, from reversibility and reach — never per agent.
- An approval needs **action, reason, reach, and what happens if you refuse.** The last is usually
  missing.
- **Asking too often destroys the control** while leaving it looking intact. Tier, batch, scope,
  measure.
- Support **pause, steer and rewind** so a correction does not throw away the work.
- Show the work rather than a fake percentage; be honest about not knowing.
- **Making an action reversible often beats gating it.**
