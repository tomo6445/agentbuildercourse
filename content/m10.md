## The least observable software most teams have shipped

Traditional observability assumes a request maps to a response, identical inputs produce identical
outputs, and failure means an error. Agents violate all three.

**The unit of interest is a decision, not a request.** "Why did it call `delete_records`?" is not
answered by any log line. It is answered by what was in context when that decision was made.

**Failures are emergent across turns.** The turn that looks wrong is often three turns downstream of
the one that *was* wrong. A truncated tool result on turn 4 becomes a false answer on turn 7, and
turn 7 is where the log looks strange.

**Identical inputs legitimately diverge.** Two runs of the same task taking different paths is normal.
Your tooling must let you compare trajectories, not just diff outputs.

::: key
You cannot debug what you cannot see. Agents are the least observable software most teams have
shipped.
:::

## What to instrument

Every one of these has earned its place by being the thing someone needed at 2am.

| Signal | What it answers |
| --- | --- |
| Turn boundaries with stop reasons | Where did it stop, and why |
| Tool spans: name, args, duration, outcome | What did it actually do |
| Token counts by category | Where is the window going (M3) |
| Context occupancy per turn | Is it degrading, and from when |
| Cache metadata | Did the cache break silently (M3, M12) |
| Cost per turn and cumulative | Which runs are expensive, and where |
| Subagent spawn tree | Who delegated what, and what came back |
| Retries and their causes | Is a retry storm forming (M12) |
| Model and prompt version | Which change did this |

That last row is the one people skip and then regret. When behaviour changes on Tuesday, "which
prompt version was this run on" is the first question, and if the answer is not in the trace you are
reconstructing it from git history and timestamps.

```python title=observability/otel.py
from opentelemetry import trace

tracer = trace.get_tracer("agent")


def traced_turn(index, request, call_model):
    with tracer.start_as_current_span("agent.turn") as span:
        span.set_attribute("agent.turn.index", index)
        span.set_attribute("agent.context.tokens", request.estimated_tokens)
        span.set_attribute("agent.prompt.version", request.prompt_version)

        response = call_model(request)

        span.set_attribute("agent.stop_reason", response.stop_reason)
        span.set_attribute("agent.tokens.input", response.usage.input_tokens)
        span.set_attribute("agent.tokens.output", response.usage.output_tokens)
        span.set_attribute("agent.tokens.cache_read", response.usage.cache_read_input_tokens)
        span.set_attribute("agent.tools.requested",
                           [b.name for b in response.content if b.type == "tool_use"])
        return response


def traced_tool(name, args, run):
    with tracer.start_as_current_span(f"tool.{name}") as span:
        span.set_attribute("tool.name", name)
        span.set_attribute("tool.args.hash", stable_hash(args))   # not the args
        try:
            result = run(args)
            span.set_attribute("tool.result.bytes", len(result))
            span.set_attribute("tool.result.truncated", getattr(result, "truncated", False))
            return result
        except Exception as exc:
            span.set_attribute("tool.error.type", type(exc).__name__)
            raise
```

## Tracing decisions without logging conversations

This is the posture that gets observability past a security review, and it is worth designing for
from the start rather than retrofitting after someone says no.

Log the **shape** of what happened, not the contents:

- `tool.args.hash` rather than the arguments. Two identical hashes on consecutive turns is your
  oscillation detector, and it reveals nothing.
- Token *counts* rather than text.
- Tool names, durations, outcomes, sizes — none of which is customer data.
- Result *size* and a truncation flag rather than the result.
- Content classifications where you need them (`contains_pii: true`) rather than content.

You can debug an enormous amount from that. Oscillation, cost blowups, cache failures, drift in turn
counts, tool error rates and truncation are all visible without a single sentence of conversation
leaving the process.

When you do need contents — and sometimes you do — make it explicit, short-retention, access-
controlled, and off by default. A debug flag on a specific session, not a firehose.

## The failure taxonomy

Seven classes. Each has a trace signature; learn to read them.

**Tool misselection.** A plausible but wrong tool for the task. *Signature:* the tool ran fine, the
result was irrelevant, and the next turn tries a different tool. *Root cause:* almost always tool
descriptions (M2).

**Argument malformation.** Right tool, wrong arguments. *Signature:* validation errors, or empty
results from a query that should have matched. *Root cause:* parameter descriptions, missing enums.

**Context degradation.** Quality falls as context fills. *Signature:* accuracy declining with turn
index; early instructions stop being followed. *Root cause:* M3.

**Goal drift.** The agent ends up doing a different, adjacent task. *Signature:* tool arguments
migrating steadily away from the original topic, and a final output on the wrong subject. No errors
anywhere.

**Oscillation.** Repeated `(tool, args)` pairs with no state change between them. *Signature:*
identical arg hashes on alternating turns. Cheapest failure to detect, if you hashed the args.

**Silent truncation.** A tool returned a fraction of the data with no marker. *Signature:* a result
size suspiciously exactly at a limit, followed by confident conclusions. This is the nastiest one,
because nothing anywhere looks like an error.

**Injection.** Retrieved content containing instructions the agent follows. *Signature:* a sudden
change in behaviour immediately after a fetch or memory read, often with tool calls unrelated to the
user's task. (M11.)

## Replay-driven debugging

The highest-leverage technique in the course, and it takes one paragraph to explain.

When a run fails at turn 22, do not re-run the task from turn 0 and hope it fails the same way. Fork
the session at turn 21, change exactly one thing, and run both branches.

```text
session_abc123, failed at turn 22
  ├── fork @21, baseline           -> fails identically. The failure is deterministic given state.
  ├── fork @21, tool desc rewritten -> passes. Root cause found.
  └── fork @21, compaction disabled -> fails. Not the compaction.
```

Three forks, one root cause, no statistics required. Compare that to re-running a stochastic task
thirty times to see whether a change helped.

This is why M5 spent time on sessions. It is also why your trace records need to be complete enough
to reconstruct state: a trace you cannot replay from is a log.

## Alerting on agent-shaped signals

HTTP 500s and latency percentiles will not tell you an agent is unwell. These will:

**Cost per task, p50 and p95.** The earliest signal of almost every problem. Retry storms, context
bloat, cache breakage and oscillation all show up here first.

**Tool error rate by tool.** One tool degrading is invisible in an aggregate error rate and obvious
per-tool.

**Turn-count distribution shift.** Not the mean — the *shape*. A growing tail means tasks are
starting to thrash before they finish, and it precedes user complaints by days.

**Cache hit rate.** A cliff means someone put a timestamp in the system prompt. Silent, expensive,
trivially detectable.

**Refusal and abstention rate.** A sudden rise means something upstream changed — a prompt edit, a
tool returning garbage, a corpus that stopped loading.

**Truncation rate.** Count it explicitly. Silent truncation is invisible by construction unless your
tools report it and you graph it.

::: autopsy The heisenbug that only failed in production
An agent that passed every eval and failed intermittently in production, roughly one run in twelve,
never reproducibly. Local runs were clean.

Trace comparison found it. Successful and failing traces were identical except for the *order* of
items in one tool's result. Under load, the backing service returned rows in nondeterministic order,
and the agent had learned — from the tool's description, which promised "most relevant first" — to
rely on the first row.

Nothing errored. No log line was wrong. It was found by diffing two traces of the same task, which
is only possible if you record enough to diff. The fix was one sentence in the tool description and
an explicit sort — but the fix was never the hard part. Seeing it was.
:::
