## Why your usual logging fails here

Normal software logging assumes three things: one request produces one response, the same input
produces the same output, and failure means an error appears.

Agents break all three.

**What you care about is a decision, not a request.** "Why did it call `delete_records`?" is not
answered by any log line. It is answered by what was in the conversation at that moment.

**Failures build up across turns.** The turn that looks wrong is often several turns after the one
that *was* wrong. A shortened tool result on turn 4 becomes a false answer on turn 7, and turn 7 is
where the log looks odd.

**Two identical runs legitimately differ.** Your tooling has to let you compare two *routes*, not
just two outputs.

::: key
You cannot debug what you cannot see. Agents are the least visible software most teams have shipped.
:::

## What to record

You started this in M1 with a list of turn records. Here is what it grows into. Every row has earned
its place by being the thing somebody needed at 2am.

| What | The question it answers |
| --- | --- |
| Each turn and why it stopped | Where did it stop, and why |
| Each tool: name, arguments, duration, outcome | What did it actually do |
| Token counts | Where is the context going (M3) |
| Cache figures | Did caching quietly break (M3) |
| Cost per turn and running total | Which runs are expensive, and where |
| Which worker did what | Who delegated what, and what came back (M9) |
| Retries and why | Is a retry storm forming (M12) |
| Model and prompt version | **Which change caused this** |

That last one gets skipped and then regretted. When behaviour changes on Tuesday, "which version of
the instructions was this run on" is the first question, and reconstructing it from commit history
and timestamps is miserable.

## Recording behaviour without recording conversations

This is the approach that gets past a security review, and it is much easier to build in from the
start than to retrofit after somebody says no.

Record the **shape** of what happened, not the contents:

- **A fingerprint of the arguments**, not the arguments. Two identical fingerprints on consecutive
  turns is your looping detector, and it reveals nothing about the data.
- **Token counts**, not text.
- **Tool names, durations, outcomes, result sizes** — none of which is customer data.
- **Flags** where you need them (`contained_personal_data: true`) rather than the content.

::: jargon Fingerprint (hash)
A short string calculated from some data. The same data always gives the same fingerprint, and the
data cannot be recovered from it.

```python
import hashlib, json

def fingerprint(arguments):
    text = json.dumps(arguments, sort_keys=True)
    return hashlib.sha256(text.encode()).hexdigest()[:12]
```

`sort_keys=True` matters: without it, the same information written in a different order gives a
different fingerprint, and your comparison silently stops working.
:::

You can diagnose an enormous amount from that. Looping, cost blowouts, broken caching, drifting turn
counts, tool error rates and silent shortening are all visible without a single sentence of
conversation leaving the process.

When you *do* need contents — and sometimes you do — make it deliberate: switched on for one specific
run, short retention, restricted access, off by default.

## Seven kinds of failure

Each leaves a recognisable trace. Learning to read these is most of what debugging an agent is.

**Wrong tool chosen.** Plausible but not right. *Looks like:* the tool ran fine, the result was
irrelevant, the next turn tries something else. *Usually caused by:* tool descriptions (M2).

**Bad arguments.** Right tool, wrong values. *Looks like:* validation errors, or empty results from a
query that should have matched. *Usually caused by:* missing parameter descriptions or missing enums.

**Context degradation.** Quality falls as the conversation grows. *Looks like:* accuracy dropping
with turn number; early instructions stop being followed. *Cause:* M3.

**Drift.** It ends up doing a different, adjacent task. *Looks like:* tool arguments moving steadily
away from the original topic, and a final answer on the wrong subject. **No errors anywhere.**

**Looping.** *Looks like:* the same tool with the same arguments on alternating turns — identical
fingerprints. Cheapest failure to detect, if you recorded the fingerprints.

**Silent shortening.** A tool returned part of the data with no marker. *Looks like:* a result sitting
suspiciously exactly on a round number, followed by confident conclusions. The nastiest one, because
nothing anywhere looks like an error.

**Injection.** Content it read contained instructions and it followed them. *Looks like:* a sudden
change in behaviour right after fetching something, often with tool calls unrelated to the task
(M11).

## Debugging by branching

The highest-value technique in the course, and it takes a paragraph.

When a run fails at turn 22, **do not** re-run the whole task and hope it fails the same way. Branch
the saved run at turn 21 (M5), change exactly one thing, and run both.

```text
run abc123, failed at turn 22
  ├── branch at 21, unchanged        -> fails identically. So it is deterministic given that state.
  ├── branch at 21, tool description rewritten -> passes. Found it.
  └── branch at 21, summarising turned off     -> still fails. Not the summarising.
```

Three branches, one cause, no statistics needed. Compare that with re-running a variable task thirty
times to see whether a change helped.

This is why M5 spent time on sessions, and why your records need to be complete enough to restart
from. **A record you cannot replay from is just a log.**

## What to watch

Server error rates and response times will not tell you an agent is unwell. These will.

**Cost per task.** The earliest signal of almost everything. Retry storms, context bloat, broken
caching and looping all show up here first.

**Tool error rate, per tool.** One tool degrading is invisible in an overall rate and obvious per
tool.

**The shape of the turn-count distribution.** Not the average — the *tail*. A growing tail means
tasks are starting to thrash before finishing, and it shows up days before users complain.

**Cache hit rate.** A cliff means somebody put a timestamp in the instructions. Silent, expensive,
trivial to detect if you are looking.

**How often it declines or abstains.** A sudden rise means something upstream changed — an edited
prompt, a tool returning nonsense, a document store that stopped loading.

**How often results were shortened.** Count it explicitly. Silent shortening is invisible by
definition unless your tools report it and you graph it.

::: autopsy The bug that only happened in production
An agent that passed every test and failed intermittently in production, about one run in twelve,
never reproducibly. Locally it was clean.

Comparing records found it. Successful and failing runs were identical except for the *order* of
items in one tool's result. Under load the backing service returned rows in a different order, and
the agent had learned — from that tool's description, which promised "most relevant first" — to rely
on the first row.

Nothing errored. No log line was wrong. It was found by comparing two records of the same task,
which is only possible if you record enough to compare. The fix was one sentence in the description
and an explicit sort — but the fix was never the hard part. Seeing it was.
:::

::: deeper Using a standard format
Rather than inventing your own, you can emit records in **OpenTelemetry** format — a widely-used
standard for this kind of data, supported by most monitoring tools.

```python
from opentelemetry import trace

tracer = trace.get_tracer("agent")

with tracer.start_as_current_span("agent.turn") as span:
    span.set_attribute("agent.turn.index", turn_number)
    span.set_attribute("agent.prompt.version", prompt_version)

    response = call_the_model(...)

    span.set_attribute("agent.stop_reason", response.stop_reason)
    span.set_attribute("agent.tokens.input", response.usage.input_tokens)
    span.set_attribute("agent.tools.requested",
                       [b.name for b in response.content if b.type == "tool_use"])
```

A **span** is one piece of work with a start, an end and some labels. Spans nest, which is what makes
a worker breakdown (M9) readable.

The gain is not the format itself — it is that existing dashboards, alerting and storage already
understand it, so you are not also building a monitoring product.
:::

## What you now know

- Ordinary logging fails because the unit of interest is a **decision**, and failures build across
  turns.
- Record turns, tools, tokens, cache figures, cost, workers, retries and **which version was
  running**.
- **Fingerprints instead of arguments** let you diagnose without recording conversations.
- Seven failure kinds, each with a recognisable signature. Silent shortening is the nastiest.
- **Branch a saved run** and change one thing. Three branches beat thirty re-runs.
- Watch cost per task, per-tool error rates, the turn-count tail, cache hits, abstentions and
  shortening.
