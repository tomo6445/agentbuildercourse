## The problem this solves

Your agent is worth roughly what it can reach. In M2 you wrote tools by hand. That works, and it
does not scale: every agent needs its own connector to every system.

Ten agents, ten systems, and you are maintaining a hundred connectors — each with its own login
handling, error handling and quirks.

::: key
An agent is worth roughly what it can reach. MCP is how it reaches.
:::

::: jargon MCP
Model Context Protocol. An agreed way for programs to offer tools to AI agents.

A "protocol" is just an agreed set of rules for talking — like agreeing everyone will speak English
in a meeting. If your system speaks MCP, any agent that speaks MCP can use it, and neither side
needs to know anything special about the other.
:::

With a shared standard it becomes ten plus ten instead of ten times ten. Somebody else's database
server works with your agent, and your internal server works with any agent.

## Three roles

- **Server** — wraps one system and offers what it can do. You might write one for your inventory
  database.
- **Client** — the part inside your agent that talks to one server.
- **Host** — your application: it holds the model, the conversation, and decides what each server is
  allowed to do.

The important thing is where trust sits.

::: warn A server is code somebody else wrote, with a voice in your model's ear
This is the part beginners miss, and it is not a small detail.

A server does not only run actions. It supplies the **tool descriptions**, and those go straight into
your model's context (M2). Text from a server is read by your model as instructions.

So connecting a server you have not reviewed is closer to running someone else's code than to
plugging in a cable. A malicious or careless one can influence what your agent does, using nothing
but its own tool descriptions.
:::

## What a server can offer

Three kinds of thing, separated by **who asks for it**.

**Tools** — the model asks. Exactly what you built in M2, and every rule from that module still
applies. A standard does not exempt you from writing a good description.

**Resources** — your application asks. Data the host chooses to include: a file, a schema, a
configuration. The model does not reach for these; your code decides when they are relevant.

**Prompts** — the user asks. Templates a person picks from a menu, like a slash-command.

The distinction is not decorative:

- Should the **model** decide when to use it? → tool
- Should **your application** decide? → resource
- Should the **user** pick it? → prompt

Making everything a tool is the standard mistake, and it is why so many servers cost so much context.

```python title=inventory_server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("inventory")


@mcp.tool()
def inventory_check_stock(sku: str, warehouse: str = "any") -> str:
    """Check available stock for a product across warehouses.

    Use this whenever someone asks whether something is in stock, how many are
    available, or where an item is held.

    Returns per-warehouse counts, a total, and when the figures were last
    refreshed. An unknown product code returns a clear message rather than an
    error — check the code with the user rather than retrying.

    Args:
        sku: The product code, for example 'AC-1180'. Not case-sensitive.
        warehouse: A specific warehouse, or 'any' for all of them.
    """
    ...
```

Read that docstring as an M2 artifact: what it does, when to use it, what comes back, what "not
found" looks like.

## Things flowing the other way

Most people write a client that lists tools and calls them, and stop. Three capabilities go the
opposite direction, and they are what make this interesting.

**Sampling** — a *server* asks *your* model to write something. A server that summarises documents
no longer needs its own model or its own bill; it asks yours.

**Elicitation** — a server asks the *user* a question mid-task. "Which of these three customers did
you mean?" — without the server needing its own interface.

**Roots** — your client declares which folders a server may work in.

::: warn Sampling is somebody else's prompt, on your bill
A server that can ask your model to generate anything, with wording it controls, is pointing a
prompt at your account and your context.

Gate it: show the user what is being asked, cap how much it may generate, and treat what comes back
as untrusted text (M11).
:::

## How it connects, and why that is a security question

Two ways, and this is not a convenience choice.

**As a program on your machine.** The server runs as a subprocess of your application. It inherits
*your* access: your files, your user account, your environment variables — including your secrets.
No network, no login needed, because there is no boundary to cross. That is the appeal and that is
the risk: running an unreviewed package means it has everything you have.

**Over the network.** Now there is a real boundary, so it needs authentication, and it can be shared
across people and machines.

| | On your machine | Over the network |
| --- | --- | --- |
| Trust | Inherits your access | Explicit, per request |
| Login | None needed | Required, with defined scope |
| Your secrets | Visible to it | Only what you grant |
| Several users | No | Yes |
| You are trusting | The package you installed | Whoever operates it |

Running one over the network means operating a service: checking credentials, rotating them, logging
who did what. Write down which you chose and why — the lab asks for exactly that.

## Fifty servers is a context problem

Remember from M2 that tool descriptions are sent **on every turn**. Connecting servers multiplies
that fast.

Six servers with nine tools each, at 270 tokens per description, is around **15,000 tokens per
turn** — before anyone says anything, whether or not a single one gets used.

::: widget mcp-budget
:::

Three fixes, cheapest first:

**Connect fewer servers.** Connect what this task needs, not everything you own.

**Tidy the server's own tools.** M2 applies: nine database-shaped operations are often three
task-shaped ones.

**Let the model search for tools.** Mark tools as not-loaded-by-default and add a search tool, so
descriptions are fetched only when relevant. Namespacing from M2 is a prerequisite — searching forty
tools called `get`, `list` and `search` just retrieves the wrong ones faster.

::: autopsy The server that ate the context window
A team connected an internal platform server with forty tools: **11,000 tokens per turn** of
descriptions, on a task that typically ran fourteen turns. So 154,000 tokens of descriptions before
the user typed anything — and the agent used, on average, three of the forty tools.

They fixed it three ways and measured each. Consolidating forty operations into eleven task-shaped
tools: 11,000 → 3,400 tokens, and *accuracy improved*, because the near-duplicates that had been
attracting each other's calls were gone. Adding tool search: 3,400 → 1,100. Connecting per task: another
third off.

The order matters. Tool search over a badly-named set just retrieves the wrong descriptions faster.
:::

::: deeper Capability negotiation, and a caching trap
When a client and server connect they exchange what each supports, rather than assuming. Servers can
also announce later that their tool list has changed.

That last one is a trap worth knowing about. Tools are sent at the very front of every request, so a
tool list that changes mid-conversation **invalidates your prompt cache** (M3) — and a chatty server
that re-announces its tools can quietly multiply your bill with no other symptom.

Check `usage.cache_read_input_tokens` after connecting anything new.
:::

## What you now know

- A **protocol** means M+N connectors instead of M×N.
- **Server, client, host** — and a server both runs actions *and* puts text into your model's context.
- **Tools** (model asks), **resources** (your app asks), **prompts** (user asks). Making everything a
  tool is the common mistake.
- **Sampling** and **elicitation** flow the other way and need gating.
- **On your machine** inherits your access; **over the network** needs authentication. That is a
  security decision.
- Connected tools cost tokens **every turn**. Consolidate, connect selectively, then add tool search.
