## Why a protocol

An agent is worth roughly what it can reach. The naive way to extend reach is one integration per
system per agent — which is M×N connectors, each with its own auth, error handling, schema
conventions and maintainer.

The Model Context Protocol replaces that with M+N. Each system gets one server; each agent gets one
client. A server someone else wrote for Postgres works with your agent, and your internal inventory
server works with any MCP-speaking client.

::: key
An agent is worth roughly what it can reach. MCP is how it reaches.
:::

The architecture is three roles:

- **Host** — the application the user interacts with. It owns the model, the conversation, and the
  decision about what any given server is allowed to do.
- **Client** — lives in the host, one per server, maintaining a stateful connection.
- **Server** — wraps one system and exposes capabilities over the protocol.

The trust boundary that matters is between host and server. **A server is untrusted code with a
plausible manner.** It supplies tool descriptions that go into your model's context — which means a
malicious or compromised server can inject instructions into your agent's prompt as easily as a
malicious web page can. Every server you connect widens your attack surface (M11); a server your
users can connect themselves widens it in a way you cannot review.

## Server primitives

Three, distinguished by **who initiates**.

**Tools** are model-invoked. The model decides to call them, and everything from M2 applies without
exception — MCP does not exempt you from tool design.

**Resources** are application-controlled, URI-addressed data the host chooses to include. A file, a
schema, a config. The host decides what goes in context; the model does not pull them.

**Prompts** are user-invoked templates — the slash-command shape. Surfaced in the UI for the user to
select.

The mapping is not decorative. If the model should decide when to use it, it is a tool. If your
application decides, it is a resource. If the user picks it, it is a prompt. Exposing everything as
tools is the standard mistake and it is why so many servers cost so much context.

```python title=server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("inventory")


@mcp.tool()
def inventory_check_stock(sku: str, warehouse: str = "any") -> str:
    """Check available stock for a SKU across warehouses.

    Use this when the user asks whether something is in stock, how many are
    available, or where an item is held. Returns per-warehouse counts plus a
    total, and the timestamp the figures were last refreshed. Returns a clear
    'unknown SKU' message rather than an error when the SKU does not exist.

    Args:
        sku: The stock keeping unit, e.g. 'AC-1180'. Case-insensitive.
        warehouse: Warehouse code, or 'any' for all warehouses.
    """
    ...


@mcp.resource("inventory://schema")
def schema() -> str:
    """The inventory database schema, for the host to include when relevant."""
    return SCHEMA_TEXT
```

That docstring is the tool description. Read it as an M2 artifact: what it does, when to use it, what
comes back, what "not found" looks like.

## The client primitives everyone skips

Most people implement a client that lists tools and calls them, and stop. Three capabilities flow the
other way, and they are what makes the protocol interesting.

**Sampling** lets a *server* ask *your* model to generate something. A server that summarises
documents no longer needs its own API key or model — it asks the client. You keep control of which
model, what it costs, and whether to allow the request at all.

**Elicitation** lets a server ask the *user* a question mid-operation. "Which of these three
matching customers did you mean?" — without the server needing its own UI.

**Roots** let the client declare which parts of the filesystem are in scope, so a server knows where
it may operate.

Sampling deserves a caution. A server that can ask your model to generate anything, with a prompt it
controls, is a prompt-injection vector pointed directly at your inference budget. Gate it: show the
user what is being requested, cap the tokens, and treat the returned text as untrusted.

## Transports are a security decision

Two transports, and the choice is not about convenience.

**stdio** — the server is a subprocess of the host. It inherits your local trust: your user account,
your filesystem, your environment variables including anything secret. No network exposure, no auth
needed, because there is no boundary to authenticate across. That is the point and also the risk: an
`npx some-mcp-server` you have not read runs with your privileges.

**Streamable HTTP** — the server is a network service. Now there is a real boundary, so it needs
authorization, and it can be shared across users and machines. Remote servers use OAuth: the host
obtains a token and presents it per request; the server enforces scopes.

The decision table:

| | stdio | Streamable HTTP |
| --- | --- | --- |
| Trust | Inherits local user | Explicit, per-request |
| Auth | None | OAuth, scoped |
| Secrets | Sees your environment | Only what you grant |
| Multi-user | No | Yes |
| Threat model | You are trusting the package | You are trusting the operator and the transport |

Ship a remote server and you have taken on operating a service: token validation, scope enforcement,
rate limiting, audit, and a rotation story. Document the threat-model change explicitly — the lab
requires it.

## Lifecycle and capability negotiation

A connection begins with an `initialize` exchange in which both sides declare what they support.
Neither assumes; both adapt. Servers can then send `list_changed` notifications when their tool set
changes at runtime.

That last one is a trap worth naming: a tool list that changes mid-session invalidates your prompt
cache (M3), because tools render at the front of the request. A chatty server that re-advertises its
tools can quietly multiply your bill. Watch `usage.cache_read_input_tokens` after connecting anything
new.

## Scaling: fifty servers is a context problem

Each connected server contributes its tool definitions to every turn. Six servers with nine tools
each at 270 tokens is about 15,000 tokens per turn — before the user says anything, on every turn,
whether or not any of it is relevant.

::: widget mcp-budget
:::

Three fixes, in increasing order of effort:

**Connect fewer servers.** Task-scoped connections rather than everything-always. The best token is
the one you never send.

**Consolidate the server's own surface.** M2 applies: nine CRUD tools shaped like a task are often
three.

**Tool search.** Mark tools `defer_loading: true` and add a search tool
(`tool_search_tool_regex_20251119` or `tool_search_tool_bm25_20251119`); definitions are retrieved on
demand and *appended*, which preserves the cache. Namespacing from M2 is the prerequisite — search
over forty tools called `get`, `list` and `search` returns noise. And never defer everything: the
search tool itself plus at least one other must remain loaded, or the request is rejected.

::: autopsy The MCP server that ate the context window
A team connected an internal platform server exposing forty tools. Real numbers: 11,000 tokens per
turn of tool definitions, on a fourteen-turn median task. Before a user typed a character, every
task was carrying 154,000 tokens of definitions — and the agent used, on average, three of the forty
tools.

They fixed it three ways and measured each. Consolidating forty CRUD tools to eleven task-shaped
ones: 11,000 → 3,400 tokens per turn, and *selection accuracy improved*, because the near-duplicates
that had been attracting each other's calls were gone. Adding tool search: 3,400 → 1,100. Scoping
connections per task: another third off. The order matters — consolidation first, because tool
search over a badly-named surface just retrieves the wrong definitions faster.
:::
